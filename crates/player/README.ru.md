# Самостоятельный Player

[English](README.md) | [Русский](README.ru.md) | [Документация](../../docs/ru/README.md)

Этот пакет содержит общий native UI Player и отдельный executable. У него
нет production-зависимости от Editor или проекта Two Arenas.

Сборка по умолчанию не включает ни одной опциональной реализации. Выбирайте native-пакеты
явно: `ui`, `arpg`, `puzzle`, `g1`, `vulkan`, `audio` и `persistence`. Окно puzzle использует
`ui,puzzle,vulkan`; ему не нужны ARPG или audio. `ui` включает UI callbacks
только для уже выбранных игровых пакетов. Установка включает нейтральные контракты Core,
привязанный к host контракт Custom и небольшой общий исходный пример вращения;
одни установленные метаданные никогда не активируют авторский модуль.
`g1` выбирает независимый исходный пакет [Crate Garden](../project-g1/README.ru.md);
UI законченной игры включается при дополнительном выборе `ui`. Запрошенные
аудио и сохранения по-прежнему требуют собственных native features.

Приложения совместно используют `composition_at`, `composition_with`, `service_registry`
и UI-функции `run_host`/`run_benchmark_host`. Editor может добавлять source contracts
через callback композиции до синхронизации метаданных. Обычные пути
диспетчеризации Player выбирают UI callbacks исходников по ID contribution.

Создавайте host для GUI через `ui::prepare_host`, затем передавайте полученный
host в `run_host` или `run_benchmark_host`. На Windows подготовка выполняется
в отдельном scoped-потоке с обязательным join: поиск MSVC может инициализировать
COM как MTA, тогда как потоку окна winit нужен STA/OLE. Ошибки подготовки
возвращаются без изменений; panic с раскруткой стека превращается в ошибку
запуска после освобождения принадлежащих подготовке ресурсов. Окно сохраняет
поддержку drag-and-drop. На Linux фабрика выполняется напрямую. Этот механизм
используют play/benchmark редактора и самостоятельного Player; headless-проверки
пакета не создают окна.
Обычный интерактивный Player использует имя игры из принятого авторского документа
как заголовок окна. Исходный UI с доступом к состоянию приложения получает
текущую диагностику сервисов/ошибок и может запросить закрытие приложения с
проверкой права; тому же UI внутри Editor не предоставляется право закрывать
Editor. См. [контракт UI](../../docs/ru/game-ui-tools.md).

Экспортированный пакет содержит `player.json` schema 2, авторский проект
format-4, выбранный native executable, необходимые ассеты, заранее собранные Custom
workers и запечатанные Vulkan artifacts, если они используются. Манифест записывает точные
native features, fingerprint данных/API SDK и SHA-256 хеши файлов. Запуск
требует точного совпадения скомпилированных features и точного активного
module/schema/state/SDK lock проекта. Обычное чтение не выполняет миграцию и никогда не заполняет
отсутствующие pins. Валидатор метаданных Editor может проверять меньшую установку,
не выдавая свой бинарник со всеми features за этот выбранный Player.

## Показ кадров на GPU

Обычный нативный вывод Vulkan публикует непрозрачный объект аренды GPU-кадра вместо пикселей CPU. На Windows отдельный производитель Vulkan передаёт изображение в WGPU/DX12 через общие ресурсы D3D12; на Linux отдельные устройства Vulkan используют выделенную память OPAQUE_FD с точным совпадением UUID устройства и драйвера. Мост интерфейса копирует RGBA8 и умножает цвет на альфа-канал на GPU в собственную текстуру `Rgba8Unorm`, сохраняя округление байтов прежнего преобразования egui без декодирования sRGB. Обычный показ не читает пиксели на CPU и не загружает их обратно. Неподдерживаемое взаимодействие графических API или его ошибка сохраняют последнее рабочее изображение и сообщают диагностику без молчаливого перехода на передачу через CPU.

Нативный производитель принимает не более одной GPU-отправки одновременно и располагает четырьмя арендуемыми выходными слотами. После приёма `render_presented` возвращает `RenderSubmission::Pending(ticket)`; `poll_presented(ticket)` без ожидания проверяет завершение и ровно один раз публикует этот запрос. `Busy` не принимает работу. `Ready(Frame)` поддерживает немедленный CPU/software-вывод. До завершения текущими остаются прежние изображение, идентичность, камера и происхождение; ожидающая работа не считается новым кадром. Данные сцены, изображения атласа, ресурсы команд и pipelines удерживаются до завершения их GPU-использования. Интерфейс отдельно удерживает каждую опубликованную аренду до фактического завершения GPU-работы потребителя. Удаление ссылки CPU или пропуск минимизированной поверхности не завершает ни одну сторону. Явный CPU/software-рендер, диагностический Glow и PNG-захват сохраняют пиксели CPU и могут синхронно ждать чтение с GPU; конфликтующий CPU-рендер отклоняется, пока нативная работа производителя ожидает завершения. Игровой swapchain и конвейер нескольких одновременных отправок производителя не добавлены.

Отмена отбрасывает публикацию без ожидания и освобождения занятых GPU-ресурсов. Проверка завершения отменённой работы может быть отложена до следующей отправки или уничтожения backend; отсутствие публикации не разрешает преждевременное повторное использование. При уничтожении рендера незавершённая работа производителя передаётся владеющему фоновому заданию освобождения; только это задание может ждать собственный fence до 30 секунд. При завершении приложения эти задания присоединяются после остановки владельцев рендера. `finish_gpu_retirements` сообщает освобождение потребителя и вложенные счётчики `producer`: registered/joined/completed/unconfirmed/failed. Таймаут, ошибка устройства, panic или отказ запуска потока освобождения сохраняют неподтверждённые ресурсы и удержание устройства вместо повторного использования потенциально занятой памяти; результат сообщается как ошибка, а не успешное завершение. Прежнее карантинное удержание при отказе освобождения владения потребителя Linux сохраняется. Исторические успешные проверки и искусственные отказы не подтверждают новые асинхронные исходники или реальную аппаратную потерю устройства.

Новые асинхронные исходники требуют отдельно привязанных проверок и независимого вывода в [асинхронном отчёте](../../docs/ru/gpu-async-20261018.md); прохождение отдельных текущих критериев не означает отсутствие ухудшения или итоговую приёмку. [Исторический GPU-отчёт](../../docs/ru/gpu-presentation-20261018.md) сохраняет результаты Windows source15/Linux source11 и прежние неудачи, включая открытый на тот момент cold-критерий. [Продолжение от 18 октября](../../docs/ru/p0-continuation-20261018.md) отдельно фиксирует последующий обычный cold PASS 40,906/39,9128549 с, Windows22/16 и WSL Linux23/16 и ограниченные native/package/lifecycle проверки своих исходников. Эти снимки не проверяют новую асинхронную реализацию и не подтверждают аппаратный Linux, реальную потерю устройства или физический scanout.

```powershell
Player.exe
Player.exe --state-root <writable-profile-folder>
Player.exe --verify-package <package-root> <evidence-folder>
Player.exe --headless-check <package-root> <evidence-folder>
Player.exe --benchmark <evidence-folder> [--state-root <writable-profile-folder>]
```

Интерактивная игра и нативный benchmark принимают необязательный `--state-root`
один раз с явно указанным доступным для записи расположением профилей. Без него
запрошенное хранилище использует пользовательское расположение данных приложения;
резервной записи рядом с пакетом или в его ресурсы нет. Параметр выбирает внешнее
состояние, а не другой корень пакета, компилятора или авторский документ.
Проверка пакета и headless-проверки отклоняют `--state-root` и не используют его
для изменения проверки.

Автоматический поиск проверяет `LOCALAPPDATA`, `XDG_DATA_HOME`, затем `HOME`;
пустые значения и неабсолютные пути пропускаются. Первые два используют
`ModuleEngine/profiles`, а `HOME` — `.local/share/ModuleEngine/profiles`.
Если абсолютный путь не задан, хранилище сообщает об ошибке конфигурации вместо
использования текущей папки. Это не меняет явно выбранные пути `--state-root`
и не гарантирует права записи: реальные ошибки хранилища остаются видимыми.

Обычный запуск и native benchmark ищут `player.json` только рядом с
executable. Проверка принимает явный корень пакета, выполняет три настоящих
фиксированных tick и сообщает фактическое состояние и статистику рендера; проверка
с рендером также сохраняет PNG 960×540. Headless-проверка сообщает `frame:null` и
не создаёт renderer или опциональный сервис. Исполнение пакета не использует поиск source
checkout, корень компилятора или policy поставки Editor. Vulkan требует
папку `.spirv` пакета, поэтому отсутствующий artifact вызывает отказ вместо
возврата к компиляции исходников.

Существующий native benchmark сохраняет прогрев из 30 кадров, по умолчанию 120 UI-отсчётов и
120 различных завершённых игровых кадров, требование физических 1920×1080, 45-секундный
watchdog и критерий неизменённой нагрузки с двадцатью врагами. Измеренные данные и
любая невыполненная цель сообщаются прямо; другой проект не удовлетворяет
этому критерию нагрузки только потому, что быстро рендерится.

Для более длительной диагностики с настоящим вводом задайте
`MODULE_ENGINE_BENCHMARK_FRAMES` целым числом от 120 до 2400. Это значение
используют оба счётчика: UI и различных кадров; прогрев и watchdog не меняются.
Отчёт содержит состояние игры и признак ввода для каждого отсчёта, а также
последнюю диагностику исходного игрового пакета. Другой игре нужна собственная
оценка нагрузки по этим данным; историческое поле ARPG `target_met` не является
критерием приёмки G1.

Для игры, открывающейся в меню, задайте `MODULE_ENGINE_BENCHMARK_ARM=manual`.
Обычная игра и управление остаются активными с видимой подсказкой ожидания F9;
прогрев, отсчёты и счётчики завершения benchmark не продвигаются до свежего
нажатия F9. F9 включает измерение один раз: собранная история callback/кадров/
времён/происхождения очищается, запускается отсчёт времени измерения и начинается
неизменённый прогрев из 30 кадров. Последующий F9 не сбрасывает идущее измерение.
Кадры, завершённые до включения, не попадают в его измеренный ряд. Включение не
добавляет игровых действий, изменений состояния или фильтрации нагрузки.
Оператор должен установить нужную игру и нагрузку обычным управлением перед F9.

У ожидания до включения собственный предел 120 секунд с явным отчётом incomplete.
После включения действует прежний 45-секундный watchdog измерения. Отчёт включает
`arming_mode`, `armed`, `arm_wait_ms`, `manual_arm_deadline_seconds` и
`measurement_watchdog_seconds`. Отсутствие переменной либо `automatic` сохраняет
прежний автоматический подсчёт; другое значение отклоняется. Фактические счётчики
renderer/bridge остаются накопительными счётчиками владельца, записанными на
первом/последнем измеренном наблюдении; включение сбрасывает только коллекции
benchmark, а не игру, сервисы или состояние GPU.

Эта явно включаемая переменная читается только командой `--benchmark`; в обычной
интерактивной игре нет benchmark-привязки F9 или подсказки ожидания. `arm_wait_ms`
начинается с инициализации окна benchmark и не измеряет запуск процесса.
Для свидетельства холодного запуска сохраняйте внешний таймер от старта процесса.
Исходные `render_success_samples`, `error_samples` и `window_visible_samples`
сохраняют признаки каждого измеренного callback независимо от исторического
решения о нагрузке с двадцатью врагами.

Нативные игровые позы могут поступать от активной проекции исходного модуля Core
до интерполяции Host и разворачивания контента. Это настоящие изменения матриц,
отдельные от позднего оформления цвета/материала. Их наличие не подтверждает FPS:
неизменные позы по-прежнему подавляются, неподдерживаемые преобразования используют
текущую позу, а ошибки рендера/проекции сохраняют последний исправный кадр.
`service_diagnostics_final` сохраняет итоговую диагностику этого экземпляра Player
независимо от результатов звука/сохранения другого экземпляра Editor или CLI.
