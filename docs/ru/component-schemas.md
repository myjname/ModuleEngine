# Схемы компонентов из исходников и композиция

[English](../component-schemas.md) | [Русский](component-schemas.md) | [Документация](README.md)

`CompositionContext` содержит установленные корневой `ModuleRegistry` и игровой `SystemRegistry`. Реестр систем владеет клонируемым `ComponentRegistry`. Регистрируйте исходное расширение один раз в корне композиции хоста вместе со схемами его компонентов, версиями реализаций и фабриками исполняемых систем. Inspector, проверка документа, Play, CLI и экспорт используют тот же контекст.

`ComponentSchema` объявляет стабильный ID компонента, один владеющий исходный модуль, версию схемы, подпись, агрегированные значения по умолчанию, типизированные поля `PropertySchema` и требования к модулям/компонентам. Версия схемы описывает контракт данных; версия реализации владеющего модуля фиксируется в документе отдельно. У общего компонента один владелец схемы, а потребителей может быть много. Включение любого потребителя в расписание активирует его типы компонентов; система владельца схемы не обязана исполняться. Владелец должен быть установлен и участвует в доступности активных модулей как поставщик данных, включая свои модульные зависимости. Это не добавляет узел в расписание. Владельцы схем, присутствующие только в корневом реестре, передают существующую версию реализации в каталог систем без дублирующего дескриптора или искусственной фабрики.

ID поля начинается с полного ID компонента, затем следуют точка и путь поля: `example.spin.speed`. Поддерживаются ключи объектов и числовые индексы массивов, например `material.base_color.0`. Область действия поля должна указывать этот компонент. Допускаются ID компонентов с общим префиксом, если объявленные поля остаются однозначными: `foo.speed` и компонент `foo.bar` могут сосуществовать, но схема `foo` не может объявлять `foo.bar.x` рядом с компонентом `foo.bar`. Регистрация отклоняет эту коллизию при любом порядке, поскольку точечные переопределения выбирают самый длинный ID компонента.
Inspector Apply/Inherit/Remove и изменение ресурсов используют то же правило `component_override_owner`, что и разрешение данных и удаление неактивных данных для runtime. Владение определяется по всем унаследованным и локальным подключениям до удаления, включая недоступные схемы. Поэтому редактирование `foo` сохраняет `foo.bar.value`, если `foo.bar` подключён; его видимость или активация не передаёт владение компоненту `foo`. Если незарегистрированное вложенное агрегированное поле в `foo` имеет такое же написание, Apply сохраняет его в локальном содержимом `foo` вместо создания точечного переопределения, которое адресовало бы `foo.bar`.
Агрегированные значения по умолчанию сохраняют вложенную структуру объектов/массивов и должны согласовываться со значением по умолчанию каждого поля. Разрешение заполняет отсутствующие значения в подключённых активных компонентах, не меняя авторские записи и не перезаписывая присутствующие значения. Значения шаблона, локальные значения и переопределения полей сохраняют приоритет. Неизвестные/неактивные записи сохраняются при редактировании и исключаются из очищенных runtime-данных.

Числа, логические значения, перечисления и ограниченный текст используют прежние типы свойств. `ObjectReference { required_components, optional }` хранит ненулевой ID объекта в пределах сцены; разрешённая цель должна существовать и иметь указанные активные компоненты. `AssetReference { kinds, optional }` хранит путь относительно проекта или стабильный `asset://id`. Виды — допустимые расширения файлов без точек, сравниваемые без учёта регистра (`["gltf", "glb"]`, `["png", "jpg", "jpeg"]` или расширение, определённое внешним модулем). Необязательные ссылки используют JSON null, а не пустую строку. Абсолютные пути, выход за корень и некорректные стабильные ID отклоняются.

`ComponentValidationContext` предоставляет метаданные сцены, вычисленные активные модули, вычисленное множество активных компонентов и необязательные метаданные ID/путей ресурсов. Production использует `Some(map)`, включая пустую карту: неизвестные ID и несовпадающие виды файлов отклоняются. `source_only` явно исключает проверку целей ссылок на ресурсы в упрощающих конструкторах Core. Проверка существования файлов, хешей и импортированных зависимостей остаётся обязанностью хоста/project-tools; Core не зависит от project-tools.

`register_with_validator` также устанавливает исходный семантический callback для разрешённой сущности и контекста проверки. Встроенные callback обеспечивают ограничения: health.current не превышает health.maximum, акторы/препятствия имеют только корневые transform, сцены порталов существуют. Они выполняются только для активных компонентов. Некорректные значения неактивных компонентов не мешают открыть авторский архив.

Активность вычисляется из существующего корневого графа/конфигурации и авторского графа исполнения; второго постоянного списка активации нет. Участие компонентов рендера следует за подключённым renderer. Требования компонентов к модулям — контракты доступности. Они не меняют порядок исполнения: `SystemDescriptor.requires` по-прежнему означает предшествующий модуль в расписании, а `SystemNode.after` называет предшествующий экземпляр. Стадии и узлы исполняются в сохранённом порядке.

`SystemRegistry::require_module(owner, dependency)` объявляет доступность native-модуля отдельно от требований к предшествующим системам. Композиция проверяет, что оба установлены и у активного владельца выбрана зависимость. Зависимостью может быть модуль схем/сервисов без исполняемого узла. Эта проверка не перемещает узлы и не переписывает `after`.

Корневой/GPU canvas во время редактирования может временно содержать незавершённые соединения. Правки сцены/исполнения используют те же проверки активных схем независимо от этих незавершённых портов. Публикация runtime и экспорт дополнительно требуют полной проверки графа; при отказе остаётся доступна последняя принятая runtime-версия.

`ComponentRegistry::asset_references` обходит зарегистрированные активные поля ресурсов, включая вложенные значения и значения по умолчанию, для общего планирования экспорта. Поэтому новый исходный компонент может добавить поля и зависимости ресурсов без специальной панели Inspector или ветви экспортера. Существующий импорт моделей/mesh остаётся отдельным процессом работы с контентом рендера.

Поставляемый исходный пример — `crates/player/src/source_modules.rs`. Его единственный вызов `install` в общей композиции Player регистрирует `example.spin` с полями speed, axis и enabled и систему, которая выдаёт реальные команды transform. Добавьте её систему в Gameplay Systems, привяжите `world` к ресурсу GameWorld и примените черновик исполнения в состоянии Stop. После этого Inspector может подключить Rotation к объекту даже в иначе пустой сцене. Измените радианы/секунду и ось, примените поля, сохраните и запустите. Тесты используют настоящую кнопку Inspector Apply, сохранение/повторное открытие, симуляцию и Full source export без специальной ветви панели.

Format4 сохраняет владельца/версию/хеши контрактов схем вместе с фиксациями модулей и состояния систем. Обычная загрузка и сохранение проверяют эти точные контракты; публикация Full-профиля и миграция известных legacy-форматов выполняются явно. См. [профили Engine](engine-profiles.md). Тестовый модуль source_modules редактора использует ту же общую регистрацию, а не устанавливает второй каталог.

Внутренние JSON-пути Inspector сохраняют точные ключи объектов отдельно от индексов массивов. Литеральные ключи с точками могут сосуществовать с вложенными полями без переименования при Apply. Неизменённые унаследованные поля не создают локальные агрегаты шаблонов; изменённые непрозрачные поля сохраняют весь свой агрегат верхнего уровня и соседние значения. См. [исправления редактирования и проверку](remaining-authoring-fixes-20261016.md).
