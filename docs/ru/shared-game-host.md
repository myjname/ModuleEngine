# Общий хост авторской игры

[English](../shared-game-host.md) | [Русский](shared-game-host.md) | [Документация](README.md)

`module-engine-host` владеет авторскими сессиями, транзакционными адаптерами Rust Custom, кандидатами рендера, кешами контента и интерактивным актором. Приложения передают один клонированный `CompositionContext`, разрешённые расположения ресурсов/компиляции/backend и `HostOptions`. У него нет production-зависимости от UI редактора, Vulkan, ARPG, Puzzle или Two Arenas. Игровые пакеты предоставляют свои чистые расширения через выбранное расписание. Модуль `game_host` редактора только определяет политику приложения и передаёт создание дальше.

## Выбор мира и рендера

`ModuleRegistry::render_route` следует фактическому соединению кадра viewport, соединению сцены renderer и соединению мира извлечения. Он проверяет зарегистрированные реализации, не создавая их. Хост использует именно этот мир и `Box<dyn FrameRenderer>` из его зарегистрированной фабрики рендера. Запасного выбора первого установленного renderer нет. Старый выбор мира в редакторе меняет встроенный узел мира графа перед входом в этот общий маршрут.

По умолчанию ECS gameplay сохраняет канонический ECS единственным владельцем изменяемого состояния и никогда не создаёт второй провайдер. Зарегистрированные провайдеры проекций наполняются из авторского мира командами remove/spawn и проверяются на точное равенство; их кеши переживают последующие тики. Legacy `Runtime`, работающий только с графом, использует те же фабрики реестра и политику маршрута независимо от авторской сессии.

`RendererAdapter` предоставляет идентичность конфигурации, ревизию зависимостей, цели управления и проверку на CPU до создания GPU. Vulkan владеет конкретными проверками проходов/HLSL/форматов. `FrameRenderer` предоставляет пиксели, переносимые controls, необязательные счётчики и необязательную синхронную подготовку кандидата. Фабрика может также реализовать независимый CPU-renderer без зависимости от Vulkan.

## Публикация кандидата

Изменение renderer проверяет текущие controls и все объявленные presets. Удаляются только controls, чьи ранее существовавшие цели были убраны; новая неизвестная цель по-прежнему вызывает отказ. Асинхронная подготовка использует отдельный экземпляр фабрики. При завершении повторно проверяются актуальные документ, время и controls до получения блокировок публикации. Отклонённые или устаревшие кандидаты сохраняют принятые документ, renderer, идентичность кадра и состояние игры. Наблюдение за зависимостями сравнивает состояния успеха и ошибки не чаще раза в 250 мс, позволяя повторить попытку после исправления внешнего include.

Синхронные кандидаты Vulkan разделяют живые device/cache, но владеют своим графом и конфигурацией исходников. Прогрев pipeline не выбирает этот кандидат. Асинхронные вызовы фабрики владеют отдельными устройствами, поэтому подготовка не может перенастроить активную обёртку. Счётчики backend показывают реальную работу; недоступные счётчики остаются нулевыми.

## Работа без рендера и опциональные сервисы

`RenderMode::Headless { world_node }` выбирает явно зарегистрированный мир без требования viewport и без вызова фабрики renderer. Контракты композиции и компонентов по-прежнему проверяются. Создание пропускает инициализацию GPU/инструментов, предварительное декодирование моделей и native-сервисы хоста. Worker публикует `frame=None`; явный вызов рендера возвращает ошибку до декодирования контента.

Активные расширения могут запрашивать общие native-сервисы. ARPG запрашивает опциональный `audio.wav` только когда его аудиосистема включена в расписание и имеет сигналы. Puzzle ничего не запрашивает. У `module-engine-host-services` по умолчанию нет feature audio; реализация WAV компилируется только при выборе. Если сервисы пропущены/отключены при создании, не создаётся ни одного экземпляра сервиса и не выполняются чтение аудиофайлов или вызовы аудиовыхода. Заглушение уже созданного сервиса сохраняет логическую диагностику событий, подавляя воспроизведение. Замена его конфигурации начинает диагностику заново.

Обработка/сброс сервисов происходят после успешной игровой транзакции. Ошибка сервиса сохраняется как неудачная активность хоста; она не может сообщать об отклонённом тике или Restart после того, как игра уже выполнила commit. Подтверждение ввода, эпоха перезапуска и отмена поставленных в очередь фронтов ввода следуют за зафиксированной операцией. Более поздние успешные кадры не скрывают ошибку сервиса молча.

У актора один общий атомарный флаг вывода из эксплуатации. UI handle может установить его, не ожидая медленного вызова Custom. Владение WAV не позволяет завершающемуся актору воспроизводить поверх голоса преемника или останавливать его. См. README crate сервисов.

## Граница UI и завершение работы

`GameWorker::spawn` получает хост и необязательный потокобезопасный callback пробуждения. Редактор предоставляет замыкание перерисовки egui. У crate хоста нет контекста egui. Снимки сохраняют фактические тик, ревизию представления и время завершённого кадра отдельно от более новых состояния или ошибок. Команды и захваченные фронты ввода ограничены; один интерактивный тик возвращает управление почтовому ящику. Отклонённый Custom, проверки эпох, приоритетный Restart и последнее рабочее состояние сохраняют прежний протокол.

Удаление UI handle сигнализирует о выводе из эксплуатации и завершении без ожидания потока. Владеющий поток уничтожает GPU/Custom/native-ресурсы. После цикла событий `finish_after_ui` сигнализирует всем оставшимся владельцам до ожидания их завершения. Произвольные побочные эффекты native-завершения после зафиксированной операции не поддаются откату.

Граница актора не позволяет медленному вызову симуляции блокировать методы UI; она не заставляет изначально медленную игровую систему укладываться в кадровый бюджет. Вывод GPU по-прежнему использует синхронное чтение на CPU. Приёмка производительности измеряется отдельно.
