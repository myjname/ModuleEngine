# Независимое ревью изменений

[English](../review.md) | [Русский](review.md) | [Документация](README.md)

Существенное изменение перед завершением проходит отдельного reviewer. Это другой
агент или человек, который не писал проверяемую реализацию; собственный повторный
проход автора не считается независимым. Новый агент получает задачу с чистым
контекстом, цель, критерии, пути к контрактам, исходный diff и доказательства.
Передавать ему вывод «всё правильно» вместо этих материалов нельзя.

## Когда и что проверять

Ревью обязательно при изменении сохранения/загрузки/истории/Assets, authored данных
и схем, Play/Custom lifecycle, Full/Team/Player поставки, выбора executable,
CI/маршрутов проверок и самих критериев приёмки. Для другого изменения оно нужно,
если затронуто несколько контрактов или есть существенный риск регрессии. Мелкая
опечатка в документации самостоятельного reviewer не требует.

До работы автор кратко записывает цель, нецели, критерии и исходные пользовательские
изменения. Перед ревью он заполняет [шаблон](review-template.md) в новом
`outputs/reviews/<task-id>/` и сохраняет source snapshot. Reviewer самостоятельно
читает AGENTS, затронутые контракты, полный относящийся к задаче diff и новые файлы,
прослеживает реальные пути выполнения и оценивает проверки. Прежние пользовательские
изменения надо видеть и сохранять; приписывать их текущей реализации нельзя.

Проверяются соответствие цели и архитектурным границам, сценарии ошибок/Cancel,
сохранность данных, пригодность fixtures и assertions, нулевые/пропущенные тесты,
связь логов с проверяемыми исходниками и явно оставшиеся пробелы. Прохождение CI
само по себе не подтверждает корректность. Тест, повторяющий алгоритм реализации,
либо успешный обход критерия не является доказательством свойства.

Reviewer не меняет реализацию и не делит с автором активный native/GPU/Cargo
прогон. Он может выполнить отдельную адресную проверку после согласования очереди
внутри текущей задачи. В отчёте разделяются прочитанные логи автора и собственные
прогоны reviewer. Подключать внешний AI-сервис, писать в другие чаты или публиковать
review в GitHub для этого процесса не требуется.

## Замечания и повторная проверка

Каждое подтверждённое замечание содержит файл/строку, условие возникновения,
наблюдаемое последствие и нарушенный критерий; при возможности — воспроизведение.
Предположение маркируется отдельно. Автор исправляет замечание либо даёт проверяемое
возражение. После исправления он повторяет относящиеся к нему проверки, а reviewer
проверяет исправление и новые затронутые пути. Несогласованное замечание остаётся
открытым; автор не закрывает его своей отметкой «принято».

В финале указываются reviewer, проверенный snapshot, разрешённые и открытые
замечания, реальные проверки и ограничения. При отсутствии независимого reviewer
результат явно имеет статус «не прошло независимое ревью» с причиной; не объявляйте
задачу полностью принятой. Новые изменения реализации/fixtures/критериев делают
прежнее ревью устаревшим: нужен новый snapshot и повторный просмотр изменившегося
объёма тем же или другим независимым reviewer. Новый commit с теми же файлами тоже
требует повторной привязки evidence к HEAD. Одни записи в `outputs/` не меняют source.

## Привязка к исходникам

Stdlib helper [review_snapshot.py](../../scripts/review_snapshot.py) требует Python
3.9+ и Git. Он только сохраняет/сверяет байты, **не выполняет ревью и не одобряет
изменение**. Capture выполняется после последних правок, до относящихся к этому
snapshot проверок; затем файлы не редактируются параллельно с ревью.

```powershell
& $python scripts/review_snapshot.py capture --output outputs/reviews/<task-id>/source.json
# Проверки и независимое ревью этого набора исходников.
& $python scripts/review_snapshot.py check outputs/reviews/<task-id>/source.json
```

В Linux используется тот же CLI с `python3`. Check возвращает 0 только при совпадении
snapshot, 1 при изменении, 2 при ошибке; ни один из кодов не является решением
reviewer. Capture не перезаписывает существующий файл. До финальной передачи автор
повторяет check, а reviewer сверяет source digest в своей записи с snapshot.

Snapshot содержит HEAD и SHA-256 каждого tracked файла, включая текущие dirty
пользовательские данные, плюс untracked файлы вне Git ignore и generated `work/`
и `outputs/`. Это включает ещё не добавленные в Git исходники, tests, workflows
и docs. Tracked файлы в этих папках всё равно учитываются. Удалённый tracked файл
фиксируется как missing; symlink — по тексту ссылки, без чтения внешнего содержимого.
Digest считается от отсортированного inventory и HEAD; время захвата не влияет.

Ignored/external sources, linked assets, toolchains и executable artifacts этим
inventory не покрываются: нужные input/artifact SHA, target/features и окружение
добавляются в evidence явно. Snapshot не является sandbox, подписью или защитой от
намеренной подмены отчёта. Helper не проверяет атрибуты доступа/исполнения и содержимое
submodules; неподдерживаемый Git item приводит к ошибке. Новая работа пользователя
после захвата тоже меняет snapshot: сохраните её и обновите привязку, не делайте reset.

Unit checks helper, без Cargo/GPU:

```powershell
& $python -B -m unittest discover -s scripts -p test_review_snapshot.py -v
```

Fixtures живут в `work/review-snapshot-tests`. Есть положительная сверка и отказы
для изменения tracked/untracked файла, добавления/удаления, другого HEAD, повреждения
snapshot и ошибки Git. Это проверка привязки evidence, а не качества ревью движка.
