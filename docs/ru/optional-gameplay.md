# Опциональные игровые пакеты

[English](../optional-gameplay.md) | [Русский](optional-gameplay.md) | [Документация](README.md)

Контракты Engine, переиспользуемые правила ARPG и конкретный проект Two Arenas имеют
отдельные границы исходников. Общий Host вынесен из Editor;
ARPG и audio — опциональные native-пакеты. Независимый Puzzle и отдельный
Player с выбранными features без ARPG прошли зафиксированную приёмку.
Editor устанавливает свои authoring-пакеты; это не требует устанавливать их
в каждом экспортированном Player.

См. завершённые этапы 4–8 в [журнале миграции](modular-runtime-progress.md)
и [пакет Player](../../crates/player/README.ru.md). Эти результаты относятся к
snapshot, указанным в соответствующих отчётах. [Текущее состояние](current-status.md) отслеживает
оставшиеся ограничения производительности, сервисов Linux и аппаратной проверки; эта страница
не является новым приёмочным прогоном.

| Граница | Ответственность исходников |
| --- | --- |
| Engine/SDK | Общая композиция, схемы, ECS, сессия/executor и переносимые контракты host. |
| `module-engine-arpg` | Переиспользуемые механики, схемы, редактируемое расписание по умолчанию и опциональное представление. |
| `module-engine-two-arenas` | Сцены, шаблоны, количества противников, настройка, пути звуковых событий и выбранные цели конкретного примера. |

## Владение Core

`module-engine-core` владеет авторскими сценами, контрактами композиции/схем,
сессией с фиксированным шагом, транзакционным исполнением систем и каноническим
`GameState.world: EcsWorld`. В нём нет типов игрока, боя, здоровья, победы или HUD.
`SystemRegistry::builtin()` устанавливает общие контракты; он
не устанавливает системы ARPG и не создаёт демонстрацию с двумя аренами.

`GameState` содержит ID сцены, время/tick симуляции, мир, непрозрачный
`module_data: BTreeMap<String, Value>` и `SessionControl`. Модуль может декодировать
собственную JSON-запись с namespace/версией, обновить типизированные данные и сохранить
запись снова. Контрольные точки Core сохраняют всю карту вместе с каждым столбцом
мира и временем жизни сущностей. Core не очищает жанровые поля каждый tick и не
интерпретирует JSON модулей для проверки равенства. Пакет может предоставить собственное семантическое
сравнение, когда в этом JSON есть локальные для процесса токены времени жизни.

Мир по-прежнему сериализуется в существующее поле `entities` как DTO сущностей.
Эта форма совместимости не создаёт второго владельца изменяемых сущностей. См.
[владение ECS](ecs-world.md).

## Пакеты ввода и событий

У `GameInput` четыре поля:

| Поле | Значение |
| --- | --- |
| `values` | Последние удерживаемые значения, определяемые модулем, например оси движения или позиция курсора. |
| `actions` | Множество имён нажатых действий; `pressed(name)` проверяет принадлежность. |
| `action_values` | Выбранный модулем контекст, захваченный вместе с пакетом нажатия, например прицел в момент атаки. |
| `restart` | Общее управление host/сессией. |

Например, атака может сохранять захваченный прицел, пока пакет в очереди использует
последние оси движения. Интерактивный worker ставит в очередь отдельные принятые
пакеты нажатий; при потреблении он копирует их действия/контекст поверх последних удерживаемых значений.
Удерживаемый ввод не содержит ни нажатых действий, ни их
захваченного контекста. Короткие кадры и неудачные ticks сохраняют ожидающие действия/контекст;
успешный фиксированный tick их потребляет. Имена ожидающих действий прямой сессии
образуют множество, поэтому повторяющиеся одинаковые имена до этого tick объединяются. Отдельная
очередь пакетов worker сохраняет принятые вхождения. Restart — явная
граница отмены.

`GameEvent { name, payload }` переносит непрозрачный JSON. Payload null сериализуется как
строка (`"Victory"`); другой payload сериализуется как одна именованная запись
(`{"Hit":{"attacker":1,"target":2,"damage":8.0}}`). Пустые имена, некорректные
карты и несколько записей отклоняются. Новые модули могут непосредственно выдавать собственные имена,
не добавляя ветви enum и не оборачивая каждое событие в `Custom`.
Core проверяет эту оболочку до публикации. Активные source contributions
могут дополнительно проверять формы принадлежащих им событий; несвязанные имена событий
остаются доступны другим модулям.

## Управление сессией

`SessionControl.halted` останавливает дальнейшие ticks симуляции. Данные результата модуля,
например победа/поражение ARPG, принадлежат его собственной записи кадра. Пауза host остаётся
отдельной командой управления worker.

`SessionControl.transition` переносит `SceneTransition` с назначением,
явными ID переносимых сущностей и необязательным смещением появления. Назначение,
переносимые ID и конечные значения появления проверяются до публикации tick.
`transition(id)` ничего не переносит; `transition_with(request)` выражает правила
сохранения модуля. Иерархия, трансформации и ссылки назначения сохраняют свой
локальный для сцены смысл. Если `spawn` задан, он заменяет локальное смещение
**каждой** явно переносимой сущности. Core не выбирает компонент `persistent`
или игрока от имени модуля.

Отказ preflight сохраняет принятое исходное состояние и ожидающее действие. Lifecycle hooks перехода/restart
имеют отдельную границу: произвольные native/процессные эффекты отказавшего
source hook `stop` нельзя отменить. Отказ после принятого tick
не обещает откатить этот предыдущий tick или все внешние lifecycle-эффекты.

## Установка исходников

Приложение устанавливает контракты пакетов в общий `SystemRegistry`:

```rust
let mut systems = module_engine_core::SystemRegistry::builtin();
module_engine_arpg::install(&mut systems)?;
```

Установка регистрирует схемы/defaults/семантические валидаторы компонентов, фабрики native
систем, hooks проверки/подготовки проекта и `GameContribution`.
Установленные владельцы схем могут предоставлять данные, не будучи запланированными потребителями.
Метаданные доступности/версий не меняют порядок авторского графа исполнения.
Неизвестный и неактивный авторский JSON сохраняется; подготовка runtime использует
точное активное множество компонентов композиции.

Hooks проекта регистрируются у установленного владельца. Core вызывает
установленные hooks; каждый пакет проверяет, активно ли его поведение. Audio hook ARPG
проверяет ссылки WAV, когда запланирован `game.audio`, и удаляет
неактивные данные звуковых событий из подготовленной runtime-копии, оставляя авторский проект
неизменным.

`GameContribution` предоставляет hooks `begin_tick`/`validate_state` и чистые callbacks для
начальных/следящих целей камеры, оформления snapshot, адаптации ввода скрипта,
проверки событий и диагностики.
Один или несколько запланированных модулей активации выбирают contribution. Одна лишь установка
его не активирует. Эти callbacks используют данные Core и не имеют типов egui,
окна или графического устройства. Текущий UI registry отдельно связывает
ID активного contribution с опциональными callbacks ввода/HUD.

Executor запускает активные hooks `begin_tick` внутри контрольной точки перед **всеми**
запланированными системами, включая независимо установленные контроллеры. ARPG готовит
там свой временный кадр, поэтому намерения текущего tick от более раннего source-контроллера
сохраняются до потребляющей системы ARPG. Эта подготовка не
меняет авторский порядок систем и откатывается при отказе tick.

`validate_state` проверяет весь мир-кандидат и данные модулей после всех
авторских систем и их поэтапных проверок, до публикации. Начальные сессии,
пакеты команд прямой сессии и объединённые переходы сцен используют те же активные
защиты пакетов. Это проверки только для чтения; они должны принимать корректное
начальное состояние пакета до инициализации систем и не должны публиковать внешние
эффекты. Так пакет может отклонить межобъектные инварианты, например пересекающиеся
ячейки puzzle, даже когда более поздняя source-система создала по отдельности корректные
компоненты. Отклонённый кандидат сохраняет прежний мир и ожидающее действие.

## Владение ARPG

`crates/gameplay-arpg` владеет восемью системами `game.*`, их схемами компонентов,
типизированными `ArpgInput`/`ArpgEvent`, `ArpgFrame`, боевыми запросами, временной обратной связью,
правилами audio проекта и переиспользуемыми `gameplay_schedule()`/`ExecutionGraphExt`.
`GameStateExt::arpg()`
декодирует его запись `arpg.frame/1`; `set_arpg(frame)` сохраняет обновлённую запись.
`ArpgInput::into_input()` и `GameInputExt` связывают его управление с общими
пакетами, включая захваченный прицел для нажатых действий. `ArpgEvent` сохраняет
устоявшееся externally tagged представление событий на границе этого пакета.

`boss.victory_on_death` — опциональная декларативная механика со значением по умолчанию
`false`. Проект может включить этот результат или установить собственную систему результата.
Переиспользуемый пакет не выбирает ID босса Two Arenas, количество врагов, маршрут
сцен или значение цели.

Features по умолчанию у crate пусты. Его опциональный feature `ui` добавляет egui для
сбора ввода, HUD и проецируемых боевых фигур. Чистое оформление вспышки попадания
остаётся доступным без egui и меняет только извлечённый render snapshot.
Сессиям Core не нужны эти типы представления или GPU. Общий
`module-engine-host` использует зарегистрированные интерфейсы renderer и поддерживает явно
заданный headless-мир. Фабрики опциональных сервисов устанавливает приложение;
при отсутствии audio endpoint не создаётся. См. `shared-game-host.md`.

## Конкретный проект-пример

`crates/example-two-arenas` зависит от Core и ARPG. Его
`module_engine_two_arenas::demo_project()` объединяет переиспользуемое расписание с
`content::build_project(execution)`. Файл контента импортирует только контракты Core
и содержит обе арены, шаблон и размещение малых монстров, настройку босса,
явный флаг победы, назначение прохода и пути звуковых событий. Метод примера
`ProjectExt::demo()` принадлежит этому проектному пакету.

`module_engine_two_arenas::document(base)` добавляет конкретный путь модели примера,
исходник/состояние Custom-контроллера, экземпляр контроллера в расписании и имя проекта
в переданный документ движка. Приложение выбирает граф движка и его
renderer/settings перед вызовом этой функции; пример не зависит от
Vulkan. Он заменяет scalar Custom source базовой демонстрации и удаляет
узлы/связи генератора speed, сохраняя переданный маршрут движка и
настройки, не относящиеся к контенту.

У ARPG нет production-зависимости от этого примера и production API
`demo_project()` или `ProjectExt::demo()`. Существующие регрессии ARPG явно
включают файл контента примера, зависящий только от Core, под `cfg(test)` и используют
закрытые в crate тестовые вспомогательные средства. Такое включение fixture сохраняет регрессионное
покрытие, не создавая production-цикл пакетов.

Регрессии Core теперь используют нейтральные установленные fixtures для часов, управления,
событий, схем, lifecycle и rollback. ARPG владеет переиспользуемыми регрессиями боя/паритета,
включая повторное использование ID сущностей и семь проецируемых визуальных тестов;
их сценарии на основе примера используют явную тестовую fixture. Пакет примера
также проверяет round trip своего контента и совместимость с контрактами ARPG.
Результаты workspace и адресного исполнения этапа 4 записаны в
[журнале миграции](modular-runtime-progress.md). Headless host и независимые
сборки Player остаются более поздними этапами приёмки.
