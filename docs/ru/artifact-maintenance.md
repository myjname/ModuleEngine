# Обслуживание воспроизводимых артефактов

[English](../artifact-maintenance.md) | [Русский](artifact-maintenance.md) | [Документация](README.md)

Запускайте `scripts/clean-artifacts.ps1` вручную, когда расход диска требует обслуживания.
По умолчанию он выполняет dry run. Он никогда не вызывается при обычном запуске приложения,
открытии/сохранении проекта или при каждой сборке Cargo.

```powershell
# Inspect the default historical fixture candidates; changes nothing.
.\scripts\clean-artifacts.ps1 -Json

# Also inspect the two optional local caches; still changes nothing.
.\scripts\clean-artifacts.ps1 -PruneIncremental -ResetCustomCache -Json

# After reviewing the dry run and closing all builds/apps/workers, apply the
# same explicitly selected policy. This command deletes the listed artifacts.
.\scripts\clean-artifacts.ps1 -Apply -PruneIncremental -ResetCustomCache -Json

# Optional: retain targets already blocked in preflight and apply only the
# planned targets. Retained blockers stay in the report and return exit code 2.
.\scripts\clean-artifacts.ps1 -Apply -KeepBlocked -PruneIncremental -ResetCustomCache -Json
```

Workspace — родитель установленного каталога скрипта, независимо от
текущего каталога оболочки. Параметра произвольного целевого пути нет.
Кандидаты по умолчанию — непосредственные дочерние каталоги `.work` с именами:

* `state-test-<PID>[-<number>...]`
* `script-test-<PID>[-<number>...]`
* `authoring-state-test-<PID>[-<number>...]`
* `player-plan-test-<PID>[-<number>...]`

По умолчанию также выбирается только дочерний `target` в исторических fixtures
`.work/authoring-asset-context-<PID>[-<number>...]`. Их создавал
тест редактора на перемещение Custom asset-context. Их исходники `compile`,
логи и тестовые данные `first`/`second` сохраняются; полные корни этих fixtures
никогда не становятся целями очистки. Текущие тесты вместо этого используют guard собственного fixture.

Подходят только числовые суффиксы. Это охватывает исторические сгенерированные fixtures и
исключает каталоги с похожим префиксом, названные вручную. Удаление этих fixtures
означает потерю сгенерированных binaries/тестовых данных; повторный запуск соответствующих
тестов воссоздаёт их. Сохраните fixture в другом месте, если диагностика его отказа
ещё нужна, прежде чем выбирать `-Apply`.

`-PruneIncremental` дополнительно выбирает ровно `target/debug/incremental`.
`-ResetCustomCache` дополнительно выбирает ровно `target/custom-workers`.
Ни одна опция не следует за внешним `CARGO_TARGET_DIR`, независимым
target-каталогом Team SDK или другой установкой. Скрипт никогда не выбирает целиком
`.work` или `target`, `.work/game-scripts`, каталоги загрузок Cargo, проекты
приложения, выходные отчёты, exports, библиотеки ресурсов, резервные каталоги, SDK или
установленные инструменты.

## Предварительная проверка и отказы

Требуется native-команда `CimCmdlets\Get-CimInstance Win32_Process`. Отказ инвентаризации
блокирует очистку, в том числе когда CIM запрещён sandbox исполнения. Запускайте
проверенный скрипт в сессии PowerShell с native-доступом к CIM; может потребоваться
сессия с повышенными правами. Нет ни обхода инвентаризации процессов, ни fallback на
неполный список процессов.

Любой активный процесс Cargo/rustc/rustdoc/Clippy блокирует обслуживание, даже если
невозможно определить его workspace. Работающий Custom worker, editor/Player или
workspace executable также блокирует его. Исторический fixture, чей PID ещё
существует, сохраняется; поэтому повторное использование PID может консервативно заблокировать старый
fixture. Скрипт никогда не завершает процессы. Закройте процесс обычным способом и повторите dry
run; не запускайте новые сборки или приложения во время apply.

Каждая рекурсивная цель — абсолютный дочерний путь разрешённого workspace, который должен
соответствовать фиксированному allowlist. Reparse points, junctions и символические ссылки
отклоняются в предках workspace, предках кандидатов и деревьях кандидатов.
Обход проверяет атрибуты до спуска, поэтому содержимое связанных назначений не
перечисляется. Заблокированные/нечитаемые файлы диагностируются пробой открытия
на эксклюзивное чтение. По умолчанию заблокированная цель предотвращает весь первоначальный apply.

`-KeepBlocked` явно сохраняет цели, заблокированные на предварительной проверке, и выбирает
только цели, уже отмеченные `planned`. Например, посторонний процесс может
повторно использовать PID старого fixture; тот останется нетронутым, пока другие безопасные
fixtures удаляются. Защита процессов не отключается. Недоступность CIM
по-прежнему блокирует весь apply, а глобальный блокирующий процесс сборки/приложения
не оставляет допустимых целей. Флаг можно передать и при dry run, чтобы
проверить выбор. `keep_blocked`, `apply_preflight_blocked`,
`retained_blocked_count` и `eligible_logical_bytes` явно отражают этот выбор
в отчёте. Сохранённые цели оставляют статус `blocked` и диагностику.

Перед каждым выбранным удалением скрипт повторяет проверки путей, native-процессов и
дерева. Новый блокирующий фактор, последующий отказ доступа или изменение процессов прерывает
оставшиеся цели даже с `-KeepBlocked`; скрипт никогда не пропускает вновь заблокированную
цель, чтобы продолжить удаление.
Удаление файловой системы не транзакционно: `failed-or-partial` означает, что цель
уже может быть частично удалена. Такой отчёт нельзя описывать как rollback или
завершённую очистку. Уже удалённые цели остаются в отчёте как `removed`.

Exit code 0 означает завершение dry-run/apply без блокирующих факторов. Exit code 2 означает,
что очистка сохранила заблокированные цели или apply был неполным. Это включает
успешное удаление допустимых целей с `-KeepBlocked`; проверяйте
отдельные статусы `removed`/`blocked`. Некорректные пути/параметры и
другие завершающие ошибки PowerShell также приводят к отказу команды, не разрешая
дальнейшее удаление. `-Json` выводит пути, статусы, блокирующие процессы и диагностику
для просмотра; командные строки процессов в него никогда не входят.

## Размер и политика кеша

`logical_bytes` суммирует длины файлов. Он полезен для сравнения групп кандидатов,
но сжатие, разреженные файлы, hard links, открытые handles и поведение файловой системы
означают, что это не число освобождённых байтов. `removed_logical_bytes` учитывает только
полностью удалённые цели. `available_bytes_before`, `available_bytes_after` и
`observed_available_bytes_delta` сообщают фактические наблюдения свободного места диска;
на эту разницу может влиять другая активность, в том числе делая её отрицательной. Сохраняйте
отчёты до/после вместо того, чтобы называть логические размеры освобождённым местом.

Сохраняйте кеши зависимостей/загрузок Cargo и обычные результаты сборок между
сессиями разработки. Они избавляют от повторного offline-восстановления зависимостей и
перекомпиляции. Очищайте debug incremental state только при явной нехватке диска
или обслуживании некорректного incremental cache; следующая debug-сборка может быть
медленнее. Сбрасывайте изолированный Custom build cache только когда его расход диска оправдывает
полную пересборку worker и все соответствующие workers/сборки завершены. Текущая компиляция Custom
использует собственный target и отключает worker incrementality. Очистка собственных
кандидатов/тестов отделена от этого исторического скрипта обслуживания;
свидетельства ошибок в исходниках/логах не удаляются через `-ResetCustomCache`.

После завершённого release-аудита явный сброс native dev-cache может использовать
`cargo clean --offline --locked --profile dev --target-dir E:\ModuleEngine\target`.
Он вне фиксированного allowlist скрипта: сначала проверьте точный target, reparse-
записи и отсутствие принадлежащих операции Cargo/app/worker процессов. Он удаляет debug-
executables и артефакты зависимостей; следующая debug-сборка холодная. Release-
executables, исходники/проектные данные и отчёты вне target/debug сохраняются.
Аудит 2026-10-15 зафиксировал эту разовую операцию в
`stage8-native-dev-cache-clean.json`, с сохранёнными хешами проекта/release.

## Изолированные проверки безопасности

```powershell
.\scripts\clean-artifacts.ps1 -SelfTest -Json
```

Self-test нельзя совмещать с `-Apply`. Он создаёт маленький уникальный
fixture `.work/clean-artifacts-tests-*`, использует синтетические списки процессов и
проверяет containment, allowlist/opt-in policy, недоступную инвентаризацию, активные сборки,
активные workers/PID, заблокированные файлы и junction к внешнему sentinel. Он не запускает
Cargo/native worker и не вызывает путь удаления. Создание junction требует
native-разрешений файловой системы Windows и может быть запрещено sandbox. Маленький
fixture, включая его junction/sentinel, намеренно сохраняется как evidence;
его путь указан в отчёте и находится вне allowlist очистки.
