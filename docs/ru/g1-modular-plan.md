# G1: переиспользуемые модули и законченная игра

[English](../g1-modular-plan.md) | [Русский](g1-modular-plan.md) | [Документация](../README.md)

## Договорённость и состояние

Пользователь разрешил реализацию после обсуждения G1 из двенадцати вопросов 26 октября 2026 года. Работа состоит из двух последовательных целей: сначала подготовить и независимо проверить переиспользуемые модули движка, затем создать на них законченную игру и провести её независимое ревью. Этот документ фиксирует договорённость и границы реализации, а не готовую функцию или результат приёмки. Текущая работа с исходниками ведётся в `TechArt/g1-foundation`; публикация этим поручением не разрешена.

G1 — классическая головоломка с толканием ящиков, прежде всего для Windows, с английским интерфейсом и десятью вручную подготовленными уровнями растущей сложности. Несколько ящиков нужно поставить на цели; кнопки, двери, бой и дополнительные механики не требуются. Уровни открываются последовательно, пройденные можно переигрывать. Успешные ходы учитываются в лучшем результате, жёсткого лимита нет. Неограниченный Undo в текущей попытке восстанавливает позиции и счётчик; Restart начинает уровень заново. Автосохранение хранит прогресс, рекорды, настройки и текущую попытку вместе с историей Undo. Continue восстанавливает её.

Визуально это простая цветная 3D-диорама с фиксированной наклонной камерой, которой видно всё поле. Стрелки/WASD и четыре экранные кнопки направлений создают одинаковые действия. У Undo и Restart есть кнопки и горячие клавиши. Нужны понятные меню, инструкции, выбор уровня, обратная связь о победе и завершении кампании, эффекты и фоновая музыка с раздельной сохраняемой громкостью. Зарегистрированный редакторский инструмент рисования по сетке создаёт уровни через обычные проверяемые транзакции сцены и истории. Публичная документация остаётся полной на английском и русском.

## Владение и выбор модулей

| Область | Переиспользуемый контракт движка | Ответственность игрового проекта |
| --- | --- | --- |
| Ввод | Именованные действия, обработка нажатия/удержания и эквивалентные действия UI | Привязки, подписи, имена действий головоломки и разрешённые действия каждого экрана |
| Сетка | Координаты, границы, занятость по слоям, атомарное перемещение и проекция в мир | Типы ящика/персонажа/цели, правила толкания, препятствия и условие решения |
| Undo | Сериализуемый типизированный журнал без произвольного ограничения количества ходов | Снимок попытки, его проверка и выбор принятой операции, создающей запись |
| Кампания | Упорядоченные стабильные ID уровней, открытие, повтор и настраиваемое сравнение результата | Десять раскладок, порядок обучения, оценка по меньшему числу ходов и конкретные экраны |
| Сохранения | Явно устанавливаемое хранилище с пространствами имён/версиями, проверяемая начальная загрузка и атомарная публикация | Схема профиля/попытки/настроек, решения о миграции и восстановление игровых данных |
| Звук | Явно запрошенный сервис, собственное многоголосное воспроизведение, зацикливание и отдельные уровни шин | Оригинальные аудиоресурсы, связь событий с эффектами и выбор музыки |
| Игровой UI | Зарегистрированные callbacks возвращают общие действия/значения; приложения одинаково отправляют их | Меню, расположение кнопок, тексты и визуальная тема |
| Редакторские инструменты | Зарегистрированные неизменяющие документ callbacks предлагают правку; Editor владеет проверкой, разрешениями и историей | Палитра сетки и правила рисования, поставляемые игровым пакетом |
| Нативная поставка | Метаданные точки сборки связывают установленных владельцев/презентации/сервисы с native features | Выбранная композиция, ресурсы, разрешённые Engine настройки и исполняемые правила игры |

Чистые модули `module-engine-game-kit` включаются независимыми Rust features и не являются фиктивными исполняемыми узлами графа. У них должны быть реальные потребители поведения и проверки отсутствующей возможности. Исполняемые системы по-прежнему регистрируются через `SystemRegistry`, сервисы — через `HostServiceRegistry`. Библиотека сама по себе не доказывает исполнение произвольного кода узлом корневого графа. Точка сборки может устанавливать конкретные пакеты; общий runtime, отправка команд и экспорт не должны ветвиться по именам ящиков, целей, уровней или презентаций игр.

Не следует добавлять фиктивные `GameContribution` для утилит: существующий contribution несёт основной контракт камеры/UI. Для G1 не нужны переписывание универсального планировщика, новый GPU API, сеть, мобильная платформа, полный визуальный Rust, скелетная анимация или полный PBR.

## Совместимость и данные

Старый одноуровневый Puzzle и Two Arenas остаются регрессионными потребителями. Прежние авторские лимиты и данные должны сохранять задокументированный смысл либо проходить явную миграцию владельца исходников; отсутствие лимита в G1 не должно молча менять смысл посторонних файлов. Авторские документы, runtime-попытки и пользовательские игровые сохранения разделены. Play в редакторе не должен перезаписывать профиль готовой игры. Неизвестный JSON остаётся непрозрачным согласно действующим контрактам.

Хранилище включается явно и использует выбранную приложением доступную для записи папку, без неявной записи в перенесённую поставку только для чтения. Отсутствующие необязательные сервисы не выполняют IO и не создают endpoints. Повреждённое, чужое или несовместимое сохранение должно дать диагностику и сохранить прежние байты; непрозрачное сохранение не является сериализованным исполнителем, GPU-устройством или процессом Custom. Сохранять можно только опубликованные принятые игровые изменения. Регистрация утилиты не должна менять основную камеру или UI игры из-за случайного порядка.

## Проверки и критерии завершения

Для цели 1 нужны целевые проверки поведения/отказов и независимое ревью модулей с реальным подключением: потребитель не из головоломки, уменьшенные композиции features, явный отказ отсутствующей/неподдерживаемой возможности, отправка действий UI, откат редакторского кандидата и жизненный цикл звука/сохранений. Счётчик или mock не заменяет заявленное нативное воспроизведение звука либо рендер Player. Нативные/GPU/сборочные задачи выполняются последовательно.

Для цели 2 нужны десять решаемых уровней, сценарии прогресса/открытия/повтора/рекорда/Undo/Continue, реальное управление мышью и клавиатурой, рисование сетки в редакторе, сохранение/открытие/экспорт, сохранность при отказах, включённые оригинальные графические и звуковые ресурсы и перенесённый Player без инструментов разработки. Перед заявлением такой поддержки нужна проверка установки на чистой машине; перенос на той же машине доказывает меньше. Нужны визуальный осмотр и полные инструкции на английском/русском. После общих изменений перепроверяются затронутые прежние потребители.

Согласованная цель Player — 1920×1080 на зафиксированном текущем ПК со средним интервалом кадров и p95 не выше 16,67 мс, включая самый тяжёлый авторский уровень, движение, Undo, UI и звук. Число вызовов рендера не равно числу разных показанных кадров. Как явно выбранный агентом первоначальный бюджет памяти, пиковый рабочий набор должен оставаться в пределах 1 ГиБ на воспроизводимом маршруте G1; это нужно измерить. Фиксируются запуск, размер поставки, устройство/драйвер, digest исходников и хеши артефактов. Этот документ не подтверждает выполнение бюджетов.

Каждая цель закрывается только после независимого заключения с привязкой к исходникам, исправления и перепроверки подтверждённых проблем в её объёме. Неудачные попытки и платформенные ограничения сохраняются. Итоговая поставка включает отчёт о работе и оценку движка: переиспользованные модули, специфичный код проекта, доказательства реальной композиции, неудобства, сильные стороны, отсутствующие возможности и непроверенные среды. Рефакторинг определяется обнаруженными проблемами контрактов, а не безразборочным удалением всех старых строк.
