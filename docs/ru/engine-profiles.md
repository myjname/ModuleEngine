# Профили Engine, совместимость и самостоятельный Player

[English](../engine-profiles.md) | [Русский](engine-profiles.md) | [Документация](README.md)

Профиль Engine задаёт опубликованную конфигурацию и доступную библиотеку модулей.
Проект формата 4 сохраняет сам профиль и точные версии контрактов в `engine_lock`:
реализации модулей, владельцев и структуру схем компонентов, схемы состояния
систем и идентификатор Custom SDK. `module_versions` остаётся единственной картой
версий модулей.

Доступность модуля в профиле не включает его автоматически. Активность определяется
подключёнными узлами, настройками и расписанием систем. Неактивные pins сохраняются
как архив; сами по себе они не требуют включать модуль в native-сборку Player.
Inspector использует контракты активных компонентов.

## Новый проект и смена контрактов

В **File → New Project** выберите **Inherit current Engine** либо, в Full,
**Choose Neutral Engine**, **Choose ARPG Engine** или **Choose Puzzle Engine**.
Затем выберите **Empty scene**, **Two arenas example** или **Crate puzzle example**.
Содержимое шаблона должно быть совместимо с выбранным профилем.

В Full новый Empty использует сохранённое расписание профиля; штатные профили
публикуют пустое расписание без ARPG. При наследовании сохраняются текущие граф
Engine и его настройки. В Team сохраняется закреплённое расписание Engine,
а редактируемый Rust-код Project заменяется пустым `update`.
Если закреплённые системы требуют определённой сцены, несовместимый шаблон
отклоняется до создания проекта. Например, Team с Puzzle Engine не создаёт
пустую сцену без обязательных board/pawn/crate.

Обычные Open, Save, Play и экспорт проверяют контракты и не обновляют их молча.
В Full команда **Tools → Publish Engine profile / update contracts** явно принимает
установленные активные контракты и создаёт новую версию профиля в рабочем документе.
**Save Project** сохраняет это изменение. Локальные правки графа и настроек Full
допустимы в пределах доступных модулей и закреплённых контрактов. В Team архитектура
Engine заморожена поставкой. Это правила авторинга, а не изоляция недоверенного кода.

## Миграция существующего проекта

Форматы 1–3 нельзя открыть с автоматическим обновлением. Создайте отдельную копию,
явно указав целевой профиль `neutral`, `arpg` или `puzzle`:
Команды приведены для корня репозитория; в Team-поставке EXE лежит в её корне.

```powershell
.\outputs\ModuleEngine.exe --migrate-copy .\game-project.json .\game-project-v4.json arpg
```

Миграция сверяет известные исходные контракты с поставляемым снимком целевых
контрактов, проверяет ресурсы и компилирует используемый Custom до публикации.
Исходный файл не переписывается. Команда выводит отчёт с хешем исходных байтов
и списком изменений; сохраните его вместе с историей проекта.

Неизвестные поля типизированных записей сохраняются в `legacy_archive`, неизвестный
неактивный JSON компонентов — в авторских данных. Неизвестный активный контракт
или некорректное известное поле отклоняет миграцию. Адаптер поддерживает известные
версии первого поставщика, а не произвольные форматы сторонних плагинов. Для
форматов 1–3 используется общий набор известных полей, без отдельной таблицы
появления каждого поля по версиям.

Для известного старого контракта `boss` миграция сохраняет прежнее поведение:
отсутствующий `victory_on_death` становится явным `true`, а заданный `false`
сохраняется. В новом переиспользуемом ARPG значение по умолчанию — `false`;
условие победы выбирает проект. Неизвестные неактивные версии не интерпретируются.

## Экспорт Windows Player

Используйте **File → Export → Windows Player…** либо команду:

```powershell
.\outputs\ModuleEngine.exe --export-game .\game-project-v4.json .\outputs\my-game
.\outputs\my-game\Player.exe
```

Назначение должно быть новой или пустой папкой. Full отдельно собирает
`module-engine-player` с нужными native features. Штатный Puzzle использует
`ui,puzzle,vulkan`, Two Arenas — `ui,arpg,vulkan,audio`. Учитываются и владельцы
активных схем, объявленных Custom, даже без расписания ARPG/Puzzle. Редакторский
exe не используется как Player. Team берёт проверенный готовый вариант; при
закреплённом `game.audio` поставка содержит варианты со звуком и без него, чтобы
разрешённое изменение звуковых cues не требовало исходников Engine.

`player.json` v2 закрепляет точный набор native features, идентификатор SDK data/API
и хеши ресурсов, Rust workers, SPIR-V и `Player.exe`. Экспорт проверяет скопированный
Player и выполняет пробный запуск с рендером до публикации папки. Для запуска
готовой игры не нужны Rust/Cargo, DXC, SDK или исходный checkout; для графического
режима нужен совместимый GPU-драйвер.

```powershell
.\outputs\my-game\Player.exe --verify-package .\outputs\my-game .\outputs\player-check
.\outputs\my-game\Player.exe --headless-check .\outputs\my-game .\outputs\headless-check
```

`--verify-package` проверяет пакет, исполнение и рендер. `--headless-check` исполняет
мир без создания GPU и native audio. Папку отчёта выбирайте отдельно от пакета.
Библиотека Player с настройками по умолчанию не зависит от UI, Vulkan, ARPG и audio.

Без запланированного произвольного Rust экспорт оставляет только ресурсы,
используемые активными схемами и сервисами. Rust может формировать asset IDs
динамически, поэтому с ним сохраняется весь объявленный manifest. Без запроса
audio-сервиса не создаётся звук и не добавляются файлы cues. Отсутствие зависимости
в native-сборке подтверждается её Cargo features/графом зависимостей; скрытая
панель, неактивный pin или исключённая из расписания система этого не доказывают.

## Custom SDK и фоновые задачи

Компиляция Custom проверяет `engine-sdk.json` до запуска Cargo, затем сверяет
идентификатор действительно слинкованного SDK. Тот же идентификатор передаётся
в пакетах worker и метаданных предварительно собранного кода. Несовпадение
отклоняет новый код и сохраняет последнюю рабочую версию с её состоянием.
Fingerprint data/API описывает контракт данных и API; стабильный Rust ABI
или совместимость представления Rust-типов в памяти он не обещает.

Отмена устаревшей подготовки или компиляции запрашивается без ожидания в UI.
Фоновые владельцы завершают работу и освобождают процессы и свои временные файлы
вне оконного цикла. Поэтому после закрытия окна процесс может ещё ждать окончания
отменяемой работы или GPU-задачи и очистки; это ожидание не блокирует работающий UI.
Отмена не гарантирует мгновенной остановки операции без точки отмены.

Ручная очистка старых воспроизводимых артефактов описана в
[artifact-maintenance.md](artifact-maintenance.md). Она не запускается при обычном
открытии или сохранении проекта; сначала просмотрите dry run.
