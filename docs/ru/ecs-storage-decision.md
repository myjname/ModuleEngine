# Решение о хранилище игрового мира

[English](../ecs-storage-decision.md) | [Русский](ecs-storage-decision.md) | [Документация](README.md)

Статус: реализовано и проверено на этапе 3. `GameState.world` владеет игровыми данными; прежняя карта сущностей остаётся только сериализованным DTO-представлением. См. [контракт API и времени жизни](ecs-world.md) и журнал доказательств этапа.

## Требования

Исходные модули регистрируют динамические ID компонентов и JSON-схемы. Сохранённый ID объекта должен переживать разрешение сцен/шаблонов, команды, экспорт и протокол Rust IPC. Весь мир, значения компонентов, ресурсы и события должны поддерживать независимую контрольную копию для отказа публикации тика. Запросы должны выбирать принадлежность компонентов без просмотра JSON-карты каждого объекта. Извлечение для рендера остаётся нейтральным.

## Сравнение подходов

| Подход | Соответствие требованиям | Дополнительная работа |
| --- | --- | --- |
| Расширить существующие таблицы компонентов `EcsWorld` | Уже есть стабильные ID, детерминированный порядок и независимое клонирование; динамические ID схем могут адресовать колонки напрямую | Колонки компонентов, запросы принадлежности, политика ссылок, проверка контрольных копий и миграция потребителей |
| Внедрить `hecs` | Типизированные запросы компонентов и непрерывное хранение архетипов независимо от нашего планировщика | Сопоставление стабильных ID, кодеки схем/native, детерминированное извлечение и явный снимок/восстановление всех установленных типов компонентов |

[Документация hecs World](https://docs.rs/hecs/latest/hecs/struct.World.html) описывает типизированные запросы и хранение архетипов. [Документация сериализации](https://docs.rs/hecs/latest/hecs/serialize/index.html) требует определённых приложением процедур, поскольку произвольные компоненты могут не реализовывать сериализацию. Это полезные возможности, но они не устраняют требования проекта к динамическим схемам и транзакциям.

Для этой итерации выбираем меньшее расширение `EcsWorld`. Решение основано на контрактах и стоимости миграции, а не на измеренном превосходстве над hecs. Динамические компоненты должны храниться в колонках с индексом по компоненту; transform, parent, color и references принадлежат тому же миру. Перенесённая карта сущностей с названием ECS этому решению не соответствует. Native gameplay читает и обновляет эти колонки; записи в форме сущности являются временными DTO для сериализации/UI/IPC.

Провайдер Object остаётся адаптером совместимости. Его независимая иерархия продолжает обслуживать legacy-примеры, но второй production-реализации игрового мира у него не появляется. Стабильные ID объектов остаются независимыми от дескрипторов хранилища.

## Приёмка и ограничения

Проверить динамические запросы принадлежности/пересечения, полный откат компонентов после ошибки валидации/commit, удаление и повторное использование без унаследованных данных, иерархию и ссылки, детерминированную сериализацию, совместимость шаблонов, извлечение сцены и поведение ARPG. В ECS-маршруте должен быть один владелец изменяемого состояния; совместимая проекция проверяется до публикации. Выбор колонок компонентов не даёт гарантий локальности кеша, параллельных запросов или производительности большого мира.
