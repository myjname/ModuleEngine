# Авторские сцены, шаблоны и Play-копии

[English](../scenes.md) | [Русский](scenes.md) | [Документация](README.md)

`GraphDocument.game` необязателен. Существующие файлы только с графом загружаются без игры.
При наличии он содержит `GameProject`: именованные сцены, входную сцену, именованные связанные
шаблоны, пути звуковых cues и авторский граф исполнения. Обычный файл проекта
сохраняет эти значения вместе с узлами графа, исходниками Rust и шейдерами.

## Идентичность и данные объектов

`AuthoredScene.objects` содержит записи `AuthoredObject`. Каждая хранит переносимый
`WorldObject` (стабильный ненулевой ID, необязательного родителя, локальный transform и цвет),
необязательный ID шаблона, значения компонентов, overrides полей и именованные ссылки
на объекты. ID уникальны внутри сцены. Загрузка сцены отклоняет отсутствующих родителей,
циклы, неконечные transform, отсутствующие шаблоны, некорректные известные игровые компоненты
и ссылки на отсутствующие объекты сцены. Имена сцен и цели порталов также
проверяются до начала Play.

Рендер остаётся независимым от формата авторских данных. `GameEntity` — это
разрешённый объект с компонентами и ссылками. `GameSession.world_objects()`
возвращает запросы объектов, нейтральные к provider. `GameSession.snapshot()` получает реальную
геометрию от выбранного world provider. Фрагмент компонента импортированной модели:

```json
{
  "components": {
    "mesh": { "path": "assets/models/demo_crystal.glb" }
  }
}
```

Пути должны быть относительными к проекту и не могут выходить выше его корня. Загрузчик
контента дополняет snapshot provider данными из `GameSession.asset_bindings()`.

Активные runtime-компоненты определяются вкладами descriptors установленных узлов
исполнения. Узлы исходного Custom могут дополнительно объявлять имена компонентов в
`params.components`. Нейтральные к renderer `mesh` и `material` по-прежнему поддерживаются.
Неактивные значения остаются в авторском проекте, но отсутствуют в runtime-сущностях
и запросах компонентов из скриптов. `prepare_runtime(registry)` удаляет неактивные компоненты сцен
и шаблонов и их overrides для данных Player/Team. Он также исключает
пути звуковых cues, когда audio-модуль неактивен. Повторное включение необязательного модуля
в исходном авторском проекте восстанавливает сохранённые данные; экспортированный очищенный
runtime-пакет не содержит этого архива. Это модульность данных, а не удаление native-
кода из executable.

## Связанные шаблоны и overrides экземпляров

`Prefab` задаёт defaults компонентов и цвет. Разрешение связанного экземпляра
каждый раз читает актуальный шаблон. Компоненты экземпляра накладывают свои непосредственные
поля на поля компонентов шаблона. `overrides` применяют явные dot paths,
такие как `health.maximum`, `melee.damage` или `color`:

```json
{
  "prefab": "small-monster",
  "components": {},
  "overrides": { "health.maximum": 80.0 }
}
```

Полная запись также содержит объект и его ссылки. Неизвестные пути override
отклоняют сцену, а не создают молча настройки с опечатками.
Изменение melee damage шаблона обновляет каждый связанный экземпляр. В примере
health override остаётся равным 80. Position/rotation/scale и parent локальны для экземпляра,
поэтому изменения шаблона никогда не переставляют размещённых монстров. Этот первый формат пока
не предоставляет вложенные иерархии prefab или defaults transform, принадлежащие шаблону.

## Редактирование и Play

`GameSession::new` принимает собственную копию проекта. Загрузка и игра разрешают эту
копию; атаки, движение, создание/удаление, cooldown и смена сцен никогда не меняют
авторский проект редактора. Stop отбрасывает сессию. Restart снова загружает
скопированную входную сцену. Поэтому сохранение проекта редактора сохраняет авторские
значения, а не мёртвых монстров или временную позицию игрока.

Пакеты world-команд проверяются целиком по принципу «всё или ничего» с одинаковой семантикой в
Object и ECS. `GameSession` сохраняет один provider между фиксированными tick и
прямым применением команд; он пересоздаёт provider при входе в сцену, переходе
или restart. Удаление объекта удаляет поддерево его потомков. Новые runtime-
объекты не становятся авторскими автоматически. Неявное применение runtime-изменений
обратно в авторскую сцену не реализовано.

Во время tick все системы сначала подготавливают и проверяют свои изменения. Затем host
проверяет и атомарно применяет полученный переносимый world-пакет до того, как
commit hooks систем опубликуют состояние скриптов или другие outputs. При ошибке восстанавливаются
собственные значения до tick и вызываются rollback hooks, включая обратный world-
пакет, если была попытка публикации. Сторонние providers должны обеспечивать
валидацию без побочных эффектов и атомарное применение команд; частному хранилищу или
внешним побочным эффектам нужна собственная семантика rollback. См.
[исполнение модулей](module-execution.md) с контрактом lifecycle.

## Переходы между сценами

Компоненты `portal` объявляют сцену назначения, радиус trigger, точку появления в назначении
и требование смерти всех противостоящих врагов. Вход в активный trigger загружает
другую сцену. Сущности с компонентами `persistent` сохраняют свои runtime-
компоненты (включая health), а авторские родители, локальные
transform и ссылки сцены назначения заменяют значения исходной сцены. Перенесённый ID, отсутствующий
в назначении, становится корневым и очищает ссылки на исходную сцену. Точка появления
портала переопределяет позицию перенесённой сущности. Остальные
объекты сцены и состояние каждой системы выгружаются и создаются заново. Переход отправляет
`GameEvent::SceneChanged`.

Provider-кандидат должен показывать в точности переданные объекты назначения
до остановки текущей сцены. Отказ загрузки сохраняет текущую сцену.
Если stop hook завершается ошибкой, его изменения видимой сцены и событий отбрасываются;
само завершение остаётся best-effort и exactly-once, поэтому внешние эффекты stop
и флаги lifecycle исполнителя нельзя откатить.

Это синхронная замена сцены с допустимой короткой паузой загрузки. Она
пока не поддерживает потоковую загрузку частей сцены или сохранение игрового прогресса на диск. Авторские данные и
игровая персистентность — отдельные обязанности.
