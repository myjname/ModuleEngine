# Исполняемые системы и авторское расписание

[English](../module-execution.md) | [Русский](module-execution.md) | [Документация](README.md)

Исходный граф рендера описывает выбранные мир, извлечение и renderer. Необязательный `GraphDocument.game.execution` описывает симуляцию. Его стадии и узлы выполняются в сохранённом порядке; executor никогда не угадывает порядок по именам модулей. Изменение этого расписания — авторская работа Engine, а значения сцены/компонентов — авторская работа Project.

## Зачем нужна эта граница

Раньше игровой процесс требовал, чтобы хост распознавал специальные узлы. Теперь `SystemRegistry` устанавливает `SystemDescriptor` и исполняемую фабрику. `SystemExecutor` создаёт каждый настроенный экземпляр из его фабрики и вызывает его жизненный цикл. Новый модуль не требует новой ветви в executor. Тесты регистрируют производителя и потребителя счётчика, которых нет во встроенном реестре, и проверяют исполнение и откат.

У каждого дескриптора есть ID модуля, явная схема состояния, типизированные порты ресурсов и необязательные требования к предшествующим модулям. `components` объявляет типы компонентов, которые потребляет система. Их поля/значения по умолчанию берутся из отдельно зарегистрированных схем компонентов; владелец схемы не обязан быть системой в расписании. Неактивные данные отсутствуют в runtime-сущностях без удаления авторских значений. `params.components` узла может явно объявлять дополнительные типы компонентов, которые потребляет Custom Rust. У каждого сохранённого `SystemNode` есть стабильный ID экземпляра, ID модуля, параметры, привязки портов к ресурсам и явные ограничения `after`. Стадия содержит упорядоченные узлы. Проверка отклоняет:

- Отсутствующие фабрики, повторяющиеся стадии/экземпляры/ресурсы и неизвестные привязки.
- Типы ресурсов, не совпадающие с объявленным типом порта.
- Чтение ресурса до того, как его произвёл более ранний узел, если ресурс не внешний.
- Обязательного предшественника, расположенного позже или отсутствующего вовсе.

Внешние ресурсы — начальные значения, принадлежащие хосту. Текущая игра объявляет `GameWorld`, `GameInput`, `GameEvents` и производимый `Positions`. `GameWorld` — типизированная возможность, доступная как `SystemContext.game`; она не копируется в большой JSON для каждого узла. `world(port)`/`world_mut(port)` проверяют объявленную привязку сервиса и возвращают переносимый мир; `resource(port)` явно отклоняет сервис GameWorld вместо возврата его null-оболочки. Для ввода и событий также есть типизированный доступ через `input_resource`, `events_resource` и `events_resource_mut`. Их JSON-оболочки ресурсов обновляются перед каждым модулем: ввод — текущий ввод хоста, а события содержат события более ранних модулей. Внутри модуля типизированный доступ к событиям канонический; JSON-оболочка — снимок на момент входа. Пользовательские типы ресурсов используют JSON-оболочки `ResourceStore` и точное сравнение имён типов. Общего независимого от языка бинарного ABI или проверки схем произвольных пользовательских JSON-данных пока нет. Native-исходникам доверяют; они могут напрямую использовать публичный контекст даже без порта. Метаданные объявляют контракты расписания и редактора, а не границу безопасности.

Native-ресурс движения/столкновений `Positions` теперь публикует каждый ID как `{"position":[x,y,z],"lifetime":token}`. Для совместимости collision также читает прежнее представление массивом координат. Текущие записи не позволяют системе, вставленной между movement и collision, применить старую начальную точку к заново созданному воплощению с тем же сохранённым ID. Native-потребители этого ресурса должны читать явную запись; это не стабильный бинарный ABI.

Изменяемый мир — `context.game.world`, каноническое ECS-хранилище. Native-системы используют запросы принадлежности компонентов и доступ к колонкам. Независимые DTO сущностей предназначены для сериализации, UI, IPC и проверки; см. [API ECS и правила времени жизни](ecs-world.md).

## Установка исходного модуля

```rust
use module_engine_core::{ExecutableSystem, SystemContext, SystemDescriptor,
    SystemRegistry};
use serde_json::Value;

struct ClockCounter;
impl ExecutableSystem for ClockCounter {
    fn step(&mut self, ctx: &mut SystemContext<'_>, state: &mut Value)
        -> Result<(), String> {
        *state = Value::from(state.as_u64().unwrap_or(0) + 1);
        ctx.events.push(module_engine_core::GameEvent::Custom {
            name: "counter".into(), payload: state.clone(),
        });
        Ok(())
    }
}

fn install_counter() -> Result<SystemRegistry, String> {
    let mut registry = SystemRegistry::builtin();
    registry.register(SystemDescriptor {
        id: "example.counter".into(), state_schema: "counter/1".into(),
        components: vec![], ports: vec![], requires: vec![],
    }, |_| Ok(Box::new(ClockCounter)))?;
    Ok(registry)
}
```

Добавьте его `SystemNode` в сохранённый граф исполнения, затем создайте `GameSession::new_with_registry(project, world_kind, registry)`. Исходные native-модули сейчас требуют пересборки приложения, как и на предыдущем этапе. Хост может зарегистрировать адаптер скомпилированного Rust Custom через ту же границу.

Установленный адаптер `custom.rust.update` объявляет `world: GameWorld` ReadWrite, `input: GameInput` Read и `events: GameEvents` ReadWrite. Его сохранённый узел должен привязать все три сервиса к соответствующим объявленным ресурсам, как и native-игровой модуль; canvas показывает эти порты и проверяет соединения. `params.source_id` узла выбирает код из `custom_sources`, а необязательный `params.components` объявляет дополнительные имена компонентов, которые использует этот код.

## Жизненный цикл, состояние и ошибки

`initialize` выполняется перед первым тиком экземпляра. `step` получает фиксированный тик, типизированный ввод, изменяемый игровой мир, события, привязки ресурсов и принадлежащее этому экземпляру JSON-состояние. `stop` вызывается в обратном порядке при замене/перезапуске сцены и завершении сессии (Editor Stop или выход Player). Каждый инициализированный экземпляр останавливается один раз; завершение пытается выполнить все hooks даже при ошибке одного из них. Drop выполняет очистку по возможности, поскольку ошибки деструктора нельзя вернуть вызывающему. Храните постоянное состояние в переданном значении состояния, а не в ненаблюдаемой глобальной переменной процесса. Встроенный модуль combat хранит в этом состоянии перезарядки, подготовку удара, направление атаки и уже поражённые цели.

Неудачный тик восстанавливает игровое состояние, принадлежащие системам состояния, значения ресурсов и события до значений перед тиком. Во время `step` системы подготавливают внешние результаты. `SystemExecutor::step_with_transaction` выполняет все шаги систем, все `validate_tick`, затем `TickTransaction::validate` и `commit` хоста, и только затем системные hooks `commit_tick`. В `GameSession` эта транзакция хоста проверяет и применяет переносимый пакет команд к выбранному провайдеру World. Поэтому отказ провайдера происходит до публикации состояния скрипта или переопределений рендера. Обычный `SystemExecutor::step` использует пустую транзакцию хоста.

Ошибка на любом шаге, проверке или публикации вызывает `rollback_tick` у вошедших систем в обратном порядке, откатывает транзакцию хоста, затем восстанавливает принадлежащие executor значения. Адаптер скомпилированного Rust использует эти hooks, чтобы сохранить прежнее состояние скрипта и переопределения рендера. Пользовательская цель хоста должна реализовать `TickTransaction::rollback` для изменений вне собственных данных executor. Native-эффекты модуля — запись файлов, вызовы ОС и скрытые изменяемые поля — требуют собственного отката; JSON-снимок не делает их обратимыми. Ошибка отката сообщается явно. Исходные модули — доверенный код, а не плагины в sandbox.

`replace_system(instance, registry, migration, reset)` подготавливает замену без изменения активной реализации. Её порты (включая типы/доступ), вклады компонентов и требования к предшествующим модулям должны совпадать с установленным контрактом. Совпадающие схемы состояния сохраняют переносимое JSON-состояние; другая схема требует явно переданного мигрированного значения или `reset = true`. Ошибки контракта, схемы и фабрики сохраняют активную и любую уже подготовленную замену. `SystemExecutor::states()` показывает подготовленное переносимое состояние или null для сброса, ожидающего инициализации. Повторная подготовка заменяет неинициализированного кандидата; завершение отменяет его без lifecycle-вызовов.

Активация ждёт, пока следующий тик достигнет авторской позиции этого экземпляра в расписании, чтобы предшествующие производители выполнились до его `initialize`. Каждая замена инициализируется, включая сохраняющую или мигрирующую состояние. Инициализатор получает выбранное переносимое состояние, но явно сохранённое/мигрированное значение имеет приоритет над любыми JSON-defaults, которые он записывает. Сброс или экземпляр, заменённый до первой инициализации, использует defaults нового инициализатора. Записи инициализации в игровые данные, ресурсы и события входят в ту же транзакцию тика хоста, что и `step`, и публикуются только при успехе тика.

После успешной инициализации старая инициализированная реализация получает одну попытку `stop` до установки кандидата. Такое завершение при замене использует копии её переносимых контекста/состояния; записи завершения отбрасываются. При неудачной инициализации кандидат очищается через `rollback_tick` и `stop`, затем отбрасывается, а старая реализация остаётся установленной. Неудачный старый `stop` также отклоняет и очищает кандидата, сохраняет прежние переносимые состояние/контекст и помечает старую реализацию для повторной инициализации на более позднем тике. Её попытка stop не повторяется до новой инициализации. Закрытые native- или внешние lifecycle-эффекты по-прежнему требуют очистки, принадлежащей модулю; копирование JSON не отменяет вызов ОС или закрытое изменение.

После установки замена следует обычной семантике отката тика. Если её первый тик или публикация хоста неудачны, она остаётся установленной с переносимым состоянием до инициализации и повторяет инициализацию на следующем тике; выведенная старая реализация не восстанавливается и не останавливается повторно. Эта исполняемая граница независима от привязанного к компилятору редактора исходников Custom. Переходы и перезапуски сессии по-прежнему создают системы из установленного реестра сессии; подготовка одного живого экземпляра не переписывает этот реестр.

## Симуляция и рендер

`GameSession::step(real_dt, input)` продвигается ровно на 1/60 секунды за тик. Он сохраняет фронт атаки до появления тика и потребляет его один раз при догоняющем выполнении нескольких тиков. Движение остаётся удерживаемым. Рендер потребляет последний неизменяемый снимок сцены независимо от количества тиков симуляции. Догоняющее выполнение ограничено 15 тиками за вызов; лишнее реальное время отбрасывается, предотвращая неограниченную очередь после паузы. Интерполяция рендера и выбор частоты симуляции остаются будущей работой.

`GameSession::new_with_world_factory` допускает отдельно реализованное редактируемое хранилище мира. Конструкторы по умолчанию используют действительно независимые хранилища Object и ECS, а не один словарь под видом двух провайдеров. Оба потребляют одни переносимые объекты и создают эквивалентные снимки.

Сессия сохраняет один провайдер World между fixed ticks и прямыми вызовами `GameSession::apply_commands`. Замена создаётся только при входе в сцену, переходе или Restart; специфичные для провайдера хранилище и кеши не пересоздаются каждый тик. Провайдер должен предоставлять стабильные переносимые объекты и реализовать `validate_commands` без побочных эффектов, а `apply_commands` — атомарно, целиком или никак. После публикации хост проверяет, что переносимые объекты провайдера совпадают с игровым состоянием кандидата. Если более поздний commit системы неудачен, хост вычисляет и применяет обратный переносимый пакет. Закрытое состояние провайдера или внешние эффекты должны сами соблюдать этот контракт отката; хост не может восстановить их из записей `WorldObject`.
