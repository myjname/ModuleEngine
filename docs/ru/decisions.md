## Выбранные детали реализации

- Нативный показ Vulkan использует непрозрачные Core-аренды кадров GPU и явные цели приложения, устраняя покадровую передачу пикселей GPU→CPU→GPU и сохраняя независимость Host/Core от нативных API. Windows использует общие ресурсы D3D12 с WGPU/DX12; Linux — выделенную память OPAQUE_FD с WGPU/Vulkan и точным совпадением UUID устройства/драйвера. Четыре аренды производителя и фактическое завершение GPU потребителя ограничивают повторное использование. Обычный нативный показ принимает один `RenderSubmission::Pending(ticket)` одновременно, без ожидания опрашивает именно этот запрос и возвращает `Busy`, не принимая работу; `Ready(Frame)` поддерживает немедленный CPU/software-вывод. Завершённые пиксели сохраняют отправленные метаданные. Ожидающая работа, отмена и фоновое освобождение сохраняют владение нативными ресурсами до реального завершения GPU. Ошибка взаимодействия API сохраняет последнее изображение и сообщает диагностику без неявного чтения на CPU. Явный CPU/software/диагностический рендер и его синхронное чтение остаются; конфликтующий CPU-рендер отклоняется при ожидающей нативной работе. Отмена отбрасывает публикацию без ожидания; уничтожение рендера передаёт незавершённую работу владеющему фоновому заданию с ограниченным ожиданием fence и явным учётом failed/unconfirmed. Игровой swapchain и несколько одновременных отправок производителя остаются отдельной работой. [Асинхронный этап GPU](gpu-async-20261018.md) требует собственных итоговых доказательств с привязкой к исходникам и независимого заключения; одно это решение не означает приёмку. [Исторические результаты с привязкой к исходникам](gpu-presentation-20261018.md) записывают Windows source15: 21 сценарий и 16 точных сравнений изображений, Host: 64 обычных теста и один ignored, экспорт/перемещение выбранного Player из 18 файлов и прохождение неизменённых критериев всеми 12 процессами обычного A/B при сохранённых данных. Проверки Linux (21 сценарий/16 сравнений) взаимодействия API отдельно привязаны к source11/WSL llvmpipe: это не сборка Linux для source15 и не аппаратная сертификация. Прежние строгий провал p95 и падения source11 остаются историческими неудачами. Малые текущие выборки подтверждают согласованные обычные критерии, а не равномерное улучшение, статистическое отсутствие ухудшения или максимальную задержку всех кадров. Холодный запуск≤45 с остаётся открытым; итоговая привязка исходников/документации и независимое заключение записываются отдельно в отчёте. Ограниченные правила коррекции только наблюдавшихся столкновений после прежних сбросов сетки определены в [GameWorker](game-worker.md); диагностика14 не является приёмкой производственной проверки.
- Rust компилируется в worker executable и обменивается owned JSON-пакетами без Rust DLL ABI. В 0.2/0.3 worker создавался на каждый tick. В 0.4 процесс постоянный, состояние явно объявлено и принадлежит host; timeout останавливает worker, а следующий tick восстанавливает последнее принятое состояние. Это не изолирует доступ к ОС и не обещает миграцию globals.
- Корневой Cargo.lock авторитетен и для зависимостей worker. Генерируемая worker-сборка проверяет версии и source пакетов перед offline --locked build; её собственный пакет имеет техническую версию 0.0.0.
- Инструменты закреплены в toolchain-manifest.json: Rust 1.99.0, DXC 1.9.2609.5. Doctor не изменяет систему; явный Restore устанавливает инструменты в каталог проекта и проверяет DXC по хешам.
- История хранит снимки документа, а merge нормализует узлы по ID и связи по входу. Конфликт оставляет базовое значение в предварительном документе и обе альтернативы в отчёте.
- Ресурсы используют AssetId, относительный путь и SHA-256. Include-зависимости HLSL экспортируются рекурсивно; макрос вместо имени include отклоняется.
- Программный renderer 0.1 сохраняется как отдельный модуль.

## Рабочие допущения

Следующие правила приняты командой для реализации; пользователь не выбирал все их детали отдельно:

1. Изменение рендерера и исходников сохраняет мир/время, когда ID, тип и параметры мира совпадают. Явная замена мира сбрасывает его.
2. Неверный кандидат сохраняет текст и последнюю рабочую версию, а диагностике виден его отказ.
3. Миграция не перезаписывает исходник при загрузке; запись существующего файла создаёт резервную копию.
4. ID модулей и их порты должны оставаться стабильными. Несовместимое изменение потребует явной миграции.
5. Позиции Rust-узлов можно переносить только при однозначном сопоставлении. Текущие ограничения описаны в Custom; полноценные постоянные AST ID пока не обещаны.

Дальнейшие продуктовые решения находятся в [открытых вопросах](questions.md).

| Решение | Реализация и граница |
| --- | --- |

| Graph/HLSL/Custom Rust hot apply доступны сейчас. | Native world/renderer/UI Rust требует сборки; hot native modules позднее. |
| Team никогда не включает Engine. | Explicit package marker, frozen blueprint и gameplay whitelist, .sdk для compiled Custom. |
| Full authoring требует полного совместимого source inventory. | Version/required files/active module paths проверяются; legitimate source edits отмечаются modified. Tools availability отдельно. |

Рабочие детали: .module-engine-package.json; личные .user/<profile>/<workspace>.json вне документа; gameplay whitelist только active custom.rust.update; SDK lock — subset полного lock по name/version/source. Team backend pins охватывают HLSL include closure и инструменты, обычные game assets остаются игровыми данными. Режим является policy, не adversarial security boundary.

Историческая граница 0.3: inactive archive сохранялся Full/local history и исключался из runtime/Team; Networking был schema test fixture; FXAA/off и ACES/Reinhard работали. Transform/Color старого Object Inspector меняли preview, авторских игровых сцен и импортера ещё не было. В 0.4 новые game-сцены сохраняются отдельно; прежние окна оставлены как legacy. Известные first-party pins старых этапов обновляются по явному списку совместимости, сторонние конфликты сохраняются; детали актуальной миграции — [graph-format.md](graph-format.md).

| Исправить текущие проблемы до начала разработки игр портфеля. | P0 включает аудит, исправление всех подтверждённых дефектов и измеренных проблем производительности существующих возможностей и итоговые перепроверки. Реализация P1 начинается после приёмки P0; неизменённые критерии ARPG/холодного запуска и обязательные проверки не могут оставаться проваленными или непроверенными. Отсутствующие будущие подсистемы остаются на следующих этапах. |

[План портфеля](portfolio-roadmap.md) предлагает матрицу минимальных пяти игр,
до пяти дополнительных кандидатов, зависимости возможностей и общие критерии
приёмки. Конкретные жанры, игровые паспорта, порядок и бюджеты — планировочные
предложения, а не дополнительные решения пользователя. Конечный портфель
подтверждает перечисленные случаи, а не универсальную пригодность любому проекту.
Каждому инкременту реализации по-прежнему нужны ограниченная цель и проверки;
решение не переоткрывает все будущие подсистемы в посторонних задачах и не объявляет
существующие performance-цели пройденными.

## Принятый языковой объём EN-01 — 22 октября 2026

До реализации игр портфеля весь собственный текст поставляемых Editor, Player и CLI переводится на английский. Это включает меню, области, подсказки, подтверждения, прогресс, ошибки, отображаемые метаданные схем/модулей, динамическую диагностику подсистем и отображаемые значения по умолчанию для новых шаблонов. Публичная документация сохраняется в полных отдельных английской и русской версиях.

Существующие авторские имена и содержимое, пути, стабильные ID, ключи API/JSON и pins модулей/схем/SDK сохраняются. Необработанная диагностика внешних компиляторов/OS и элементы нативного файлового диалога, принадлежащие OS, сохраняют исходный язык. Unicode-фикстуры регрессионных тестов и непрозрачные комментарии исходников не переводятся. Не добавляются система локализации, выбор языка, зависимость, миграция формата или переработка runtime. Существующие проекты не перезаписываются ради перевода авторского текста.

Приёмка требует классифицированного inventory текста продукта, применимых тестов и реальных сценариев текущих Editor/Player/CLI, проверки отрисованных надписей и независимого ревью с привязкой к исходникам/артефактам. Исторические доказательства P0 сохраняют свой объём; сам перевод не подтверждает повторно timing, аппаратный Linux или физический путь от ввода до показа. См. [контракт языка интерфейса](editor-workflow.md#ui-language).

## Принятое изменение показа в P0 — 17 октября 2026

Пользователь одобрил отделение фиксированной симуляции 60 Гц от более частого
показа настоящих интерполированных состояний для исправления измеренного
провала cadence Player. Обычная интерполяция между завершёнными состояниями
добавляет примерно один фиксированный такт визуальной задержки. Она сохраняет
авторитетную игровую логику, выполнение ввода/событий/Custom, авторские данные
и прежние критерии mean/p95/нагрузки. Дополнительные кадры между тактами должны
использовать изменённые вычисленные позы или камеру; повтор того же представления
или изменение счётчиков/временных меток не подтверждают успех производительности.
Истории нужны явные границы времени жизни и разрывов, включая сигнал модуля
для телепортации, смену сцены и принятые замены кода/конфигурации. Реализация
и итоговая native-проверка входят в P0; одно это решение не закрывает проваленный
критерий. См. [общий Host](shared-game-host.md).
