# Исполнение Game вне UI

[English](../game-worker.md) | [Русский](game-worker.md) | [Документация](README.md)

Нативные Editor и Player передают `GameHost` постоянному фоновому исполнителю `GameWorker`. Он владеет симуляцией, экземплярами Rust Custom, игровым аудио, рендером и подготовкой изменений. UI получает последний завершённый `Arc<GameSnapshot>` и отправляет команды. Проверочные CLI-сценарии сохраняют синхронный `GameHost`, чтобы воспроизводить заданное число действий; отдельный `--game-worker-check` проверяет именно асинхронный путь.

## Зачем это нужно

До переноса один UI-кадр мог выполнить до 15 догоняющих фиксированных обновлений. В диагностике Custom с задержкой 80 мс занимал суммарно около 1,28 секунды: в это время окно не обрабатывало события. Простое ограничение догоняния сократило бы зависание, но оставило бы каждый медленный вызов на потоке окна.

Теперь UI не выполняет `step`, Vulkan readback и запросы состояния Custom. Методы `latest`, `submit_input`, `try_command` используют только короткие `try_lock` собственных почтовых ящиков. Если они заняты, чтение возвращает предыдущий снимок, а отправка возвращает исходную команду для повторной попытки. Ожидания завершения tick или блокировки ScriptSlot в этих методах нет.

Медленный алгоритм всё ещё замедляет игру. Симуляция и игровой рендер принадлежат одному исполнителю: при долгом tick окно показывает последний готовый кадр. Это сохраняет отзывчивость редактора, но не превращает алгоритм длительностью 80 мс в симуляцию 60 Гц. Стоимость tick и накопленное отставание показываются отдельно.

## Обновления и ввод

Фиксированный шаг остаётся 1/60 секунды. За один оборот исполнитель выполняет не более одного tick, затем снова проверяет команды. Необработанное время сохраняется в accumulator с пределом 0,25 секунды; бесконечной очереди догоняющих tick нет. Пауза не накапливает время для последующего рывка.

Удерживаемые движение и направление прицеливания заменяются последним вводом. Нажатия Attack/Interact/Restart имеют последовательные номера и отдельную ограниченную очередь. Принятое нажатие подтверждается только после завершённой операции; повторный показ снимка не повторяет атаку. Restart явно отменяет старую очередь действий. UI хранит неотправленные действия и повторяет попытку, не ожидая освобождения очереди.

Команды управления имеют request ID, ответы и ограниченную историю. Совпадающие повторные запросы не применяются второй раз. Размер viewport является настройкой последнего значения. Графические изменения подготавливаются отдельно; пока кандидат не принят, работает прежний рендер. Снимок содержит камеру, принятый документ, диагностические сообщения и состояние подготовки.

<a id="интерполированный-показ"></a>

## Интерполированный показ

Интерактивный владелец планирует показ по отдельной сетке дедлайнов 120 Гц;
симуляция остаётся фиксированной на 60 Гц. Это целевая частота планировщика,
не гарантия частоты вывода/экрана. Пропущенные render-слоты пропускаются без
догоняющей очереди. Ограниченные итерации владельца проверяют команды/завершение.
Ожидание использует ближайший дедлайн симуляции, показа или подготовки и прежнее
правило прерываемого пробуждения. Глобальные настройки таймера Windows и активное ожидание
не добавляются.

Windows использует принадлежащий владельцу high-resolution waitable timer
и auto-reset wake event для точных прерываемых дедлайнов. Ввод, команды, retirement
и финальный drain сигнализируют тому же пути пробуждения; сигнал до ожидания
остаётся ожидающим. Ошибка native handle/timer/wait переключает на ограниченное
стандартное ожидание потока без заявления поддержки высокой точности. Linux
использует стандартные park/unpark. Перед native- или стандартным пробуждением
сохраняется собственный флаг, объединяющий уведомления. Блокирующие библиотеки,
например канал ответа Custom, не могут потребить этот флаг вместе с общим
park-токеном потока. Стандартное ожидание перепроверяет его после каждого ложного
пробуждения или старого токена, отсчитывая единый монотонный бюджет времени.
Снимки содержат `deadline_wait_strategy` и
`deadline_wait_error`; Player сообщает реально наблюдавшиеся стратегии/ошибки.
Платформенные проверки и результаты native-замеров производительности вместе
с их границами приведены в [отчёте P0](p0-stabilization-20261017.md).

Обычный таймаут Windows служит защитой от отказа, а не дедлайном показа. Каждое
ожидание запускает native-таймер один раз и сохраняет один монотонный watchdog
на запрошенную длительность плюс 100 мс. Ранний обычный таймаут повторяет ожидание
того же запущенного таймера. Повторы используют положительный блокирующий таймаут
с минимумом 100 мс; последний повтор может превысить логический watchdog на этот
минимум плюс задержку часов и планировщика ОС. Исправные сигналы таймера/события
возвращают управление сразу, без этой добавки. Если сломан сам механизм
пробуждения, мгновенное прерывание не гарантируется; таймер/watchdog ограничивает
восстановление, а UI продолжает работать независимо.

Alpha использует измеренное ожидающее/прошедшее время и не превышает 1. При
отставании симуляции показывается завершённое состояние без экстраполяции через
backlog. Pause/ошибка используют текущее состояние без цикла 120 Гц. Для
неизменного вычисленного представления Host возвращает `None`, сохраняя кадр/время.
[Контракт Host](shared-game-host.md#фиксированная-симуляция-и-интерполированный-показ)
определяет безопасную интерполяцию, разрывы и визуальную задержку около такта.
Медленный Custom всё ещё задерживает владельца; дополнительный показ не запускает
игровые такты и не скрывает отставание симуляции.

`GameSnapshot.frame_presentation` относится к завершённым пикселям: actor ID,
epoch, успешный serial, исходная revision, фактическая камера и provenance Host.
`frame_tick`/`frame_revision` сохраняют исходный смысл. `sequence` считает
публикации статуса, не кадры. Только успех меняет identity и записывает
`frame_completed_at`; `None`/ошибка сохраняют весь прежний набор, даже если
состояние/эпоха снимка меняются. `camera` использует камеру завершённого кадра
для проекции ввода. Player отдельно фиксирует происхождение кадров и прогресс
симуляции; изменение счётчиков не доказывает cadence. Для снимка P0 от 17 октября 2026 года привязанные к исходникам Windows-измерения проходили неизменённые критерии native ARPG и target-cold; дополнительные проверки Linux в том же историческом объёме проходили применимые native/package и функциональные Puzzle/Team/перемещённый Player проверки на WSLg/X11 software Vulkan. Linux-результат не является приёмкой ARPG FPS, cold, hardware или Wayland. Исправленный Scene-input контракт имеет адресные Windows/Linux green-доказательства; три Scene manipulators отдельно подтверждены foreground-сессией. Точные snapshots, artifacts, failed runs, границы доказательств и статус итогового независимого решения — в [P0-отчёте](p0-stabilization-20261017.md).

## GPU-аренды и backpressure

Нативные снимки могут содержать `Frame.gpu` с пустым `rgba`. Рендер допускает одну ожидающую отправку производителя и четыре арендуемых выходных слота, не ожидая обычное завершение GPU и не читая пиксели на CPU. Приём Ready/Pending потребляет только зафиксированный префикс одноразовых команд; Busy и ошибка до отправки сохраняют его. Последующая ошибка GPU не повторяет принятые команды. Только завершение точного ticket продвигает набор завершённого кадра; ожидающая работа, Busy, повтор изображения и ошибки сохраняют прежние кадр/происхождение/время завершения/камеру.

Владелец опрашивает ожидающее завершение до симуляции и независимо от сроков показа, включая paused/static/hidden views. Готовый результат сразу публикуется в latest snapshot до потенциально медленного следующего шага. После каждой фактической попытки шага, включая успех или rollback, завершение опрашивается вновь и публикуется до приёма следующего рендера; готовое изображение не задерживается за ещё одним tick или ожиданием опроса. Фактический ожидающий ticket добавляет ограниченный срок пробуждения 1 мс; один сохранённый готовый кадр не запускает этот цикл опроса. Сам опрос завершения не отправляет следующий запрос и не продвигает сетку отправки; приём сохраняет прежнее расписание абсолютных сроков с пропуском пропущенных слотов. Завершение использует отправленные камеру, source revision, tick и происхождение, а не более новое изменяемое состояние. Restart, сброс истории при Play/pause и инвалидирующие изменения сцены/документа/контента/цели отбрасывают устаревшую ожидающую публикацию; отсоединение UI/Stop не ждёт fence производителя. Общие панели Scene направляют готовые кадры по владельцу и удаляют скрытых/закрытых владельцев согласно [контракту Host](shared-game-host.md#native-frame-ownership). Мост интерфейса отдельно владеет фактическим завершением потребителя; явная диагностика сохраняет синхронное чтение с GPU.

Новые асинхронные исходники требуют отдельно привязанных проверок и независимого вывода в [асинхронном отчёте](gpu-async-20261018.md); прохождение отдельных текущих критериев не означает отсутствие ухудшения или итоговую приёмку. [Исторический GPU-отчёт](gpu-presentation-20261018.md) сохраняет результаты Windows source15/Linux source11 и прежние неудачи, включая открытый на тот момент cold-критерий. [Продолжение от 18 октября](p0-continuation-20261018.md) отдельно фиксирует последующий обычный cold PASS 40,906/39,9128549 с, Windows22/16 и WSL Linux23/16 и ограниченные native/package/lifecycle проверки своих исходников. Эти снимки не проверяют новую асинхронную реализацию и не подтверждают аппаратный Linux, реальную потерю устройства или физический scanout.

`PresentationPhase` сохраняет прежнюю одноразовую коррекцию наблюдавшегося успешного шага с продвижением симуляции, достигшего/пересёкшего срок рендера; обычные шаги без столкновения сохраняют абсолютную сетку показа. Для синхронной успешной публикации по-прежнему требуются совпадающие epoch/текущий tick и конечная неотрицательная фаза меньше существующего интервала8,333333мс.

Для асинхронного flight, пересекающего шаг, владелец сохраняет закрытую внутри crate идентичность `(ticket, generation, source_revision, current_tick)` отправленного запроса, epoch актора и зафиксированный срок рендера. Столкновение записывается, только если один и тот же точный flight существует до и после одного успешного шага, этот шаг продвигает ровно один tick от отправленного current tick, а зафиксированный срок достигнут к концу шага. Вторая попытка шага инвалидирует наблюдение; сбросы, ошибки, отмена или отсутствующий/чужой/заменённый flight не наследуют его. Последующее допустимое завершение должно совпадать по идентичности, отправленному происхождению, epoch, записанному единственному продвинутому live tick и тому же зафиксированному сроку, при Playing без fault. Конечная фаза в `[0, 8.333333 ms)` обеспечивает требуемый запас времени. Лишь тогда разрешённая коррекция один раз переносит следующий срок в `max(existing next deadline, completion + interval)`, сохраняя уже более поздний срок. Само Pending/Busy/пустой опрос или неуспешный шаг её не запускают.

Повторное разрешение возможно только при прежних сбросах сетки: Play/возобновление, фактическое допустимое изменение viewport, принятое применение/инвалидация и успешный Restart во время игры; Pause отключает его. Политика не меняет метаданные отправленного/завершённого кадра, часы/состояние симуляции, камеру/происхождение и сохраняет fixed60Hz-симуляцию и целевое планирование показа120Hz. Новый лимит, принудительная фаза или постоянная перепривязка сетки к завершениям не добавлены; итоговые тесты и производительность с привязкой к исходникам относятся к асинхронному отчёту.

<a id="play-stop-и-custom"></a>

## Play, Stop и Custom

Pause меняет состояние исполнителя после текущей операции. UI продолжает работать во время её завершения. Stop отсоединяет текущего исполнителя и возвращает авторскую сцену; будущие снимки старого исполнителя больше не принимаются. Закрытие и замена GameWorker только сигнализируют остановку и не вызывают `join` на UI. Освобождение его Host, GPU и дочерних процессов выполняет владеющий поток.

После возврата из оконного цикла `main` вызывает `finish_after_ui`: сначала сигнализирует всем ещё живым владельцам, затем дожидается их завершения вне UI. Так процесс приложения не выходит раньше уничтожения persistent Rust-процессов. Во время работы редактора удаление исполнителя остаётся неблокирующим.

Подготовка Host, компиляция Custom и авторский preview зарегистрированы как отменяемые фоновые задачи. После владельцев игры завершение приложения отменяет и дожидается этих задач, затем очищает их артефакты. На Windows Cargo и Custom принадлежат отдельным Job Object: отмена завершает принадлежащее приложению дерево процессов напрямую и ждёт его выхода перед освобождением файлов. Закрытие последнего handle при аварийном выходе владельца также завершает его дочерние процессы. Запуск `taskkill` для этого не используется. Это управление временем жизни процессов, не защитная песочница для пользовательского кода.

Restart использует общий `GameHost::restart`: пересоздаёт состояние мира и Custom, сбрасывает команды рендеру, звук и цель камеры. Он увеличивает epoch сессии. Скомпилированный Custom, начатый для старого исполнителя или epoch, отклоняется. Это предотвращает применение запоздавшей сборки после Restart или замены проекта.

При обычном Apply совместимое состояние сохраняется. Несовместимый кандидат остаётся у исполнителя; UI получает исходник и причину отказа, а Reset/Migration отправляет отдельной явной командой. Изменённый после отказа текст не применяется через старый кандидат. Ошибка tick останавливает повторные попытки до явного Restart или успешного применения Custom; перерисовка окна сама не запускает неисправный код заново.

## Как проверять

```powershell
.\outputs\ModuleEngine.exe --game-worker-check game-project-v4.json outputs\verification-v04\game-worker
.\verify.ps1 -NativeBenchmarks
```

Worker acceptance использует настоящий скомпилированный Rust Custom и проверяет почтовые ящики во время его работы, доставку нажатий, управление сессией и устаревшие кандидаты. Нативные benchmark отдельно измеряют UI и завершение новых игровых кадров. Повторное отображение прежнего `Frame` не считается новым игровым кадром. Общие результаты аудита и ограничения находятся в [stability-audit.md](stability-audit.md).
