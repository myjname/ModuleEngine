# Custom Rust 0.4

Custom хранит настоящий Rust в custom_sources[source_id]. Визуальное представление помогает менять известные фрагменты; компилятор проверяет и исполняет весь исходник. Неподдержанный визуально код сохраняется opaque-текстом, а не заменяется приближённым поведением.

## Исполнение и применение

Поддержаны две точки входа. Один source_id в графе относится к одному режиму: speed или update; использование того же ID в обоих типах узлов отклоняется проверкой графа. Один файл может содержать helper-функции, но выбранную точку входа определяет режим узла.

В `game.execution` узел `custom.rust.update` имеет обязательные bindings `world: GameWorld` ReadWrite, `input: GameInput` Read и `events: GameEvents` ReadWrite. Их показывает окно Gameplay Systems; неправильный тип или отсутствующий binding отклоняется при проверке кандидата. Код выбирается через `params.source_id`, дополнительные используемые им компоненты — через `params.components`. Это отдельный контракт игрового планировщика; визуальное редактирование самого Rust остаётся частичным, как описано ниже.

Пример scalar для прежнего графового Runtime:

~~~rust
fn speed(time: f64, base: f64) -> f64 {
    base + time.sin() * 0.25
}
~~~

~~~rust
fn update(ctx: &mut ScriptContext) {
    let x = ctx.time.sin() as f32;
    ctx.set_position(1, [x, 0.4, 0.0]);
    ctx.set_color(1, [75, 205, 245, 255]);
    ctx.set_render_parameter("tonemap", "exposure", 1.4);
}
~~~

ID "tonemap" здесь — ID узла прохода, не имя его module. В legacy корневом Graph узел custom.rust.update выдаёт WorldCommands и RenderCommands; исполняются только подключённые выходы. Для обоих назначений соедините commands с миром и renderer. В игровом game.execution узел того же module устанавливает GameHost adapter: команды мира/рендера и события проходят общую tick-транзакцию без этих legacy выходных pins. Изменение списка ctx.objects само по себе не изменяет мир в обоих маршрутах: используйте команды.

В редакторе кнопка «Применить Rust» запускает компиляцию кандидата в фоне. Визуальная правка также меняет исходник и запрашивает компиляцию. Успех заменяет активный executable; ошибка сохраняет предыдущую рабочую версию, ошибочный текст и диагностику. Если первая компиляция update не прошла, активной командной программы ещё нет. Для speed сохраняется ограниченный scalar preview, пока нет скомпилированной версии.

ScriptCompiler создаёт Cargo worker с обычной проверкой типов rustc. Зависимости — std, module-engine-core и serde_json из корневого Cargo.lock. Worker lock проверяется как подмножество корневых пакетов по name/version/source, затем применяется offline --locked build. Добавление произвольных внешних crates в Custom пока не имеет UI/контракта.

Родной target можно задать через `CARGO_BUILD_TARGET` или `[build].target` в Cargo config. Компилятор берёт фактический executable из Cargo JSON, включая layout `target/<triple>/debug`, вместо предположения о `target/debug`. Worker предназначен для текущего native host: generated build script подтверждает HOST=TARGET, формат и архитектура PE/ELF проверяются до SDK probe. Cross-target Custom отвергается; самостоятельный Player для другой ОС собирается на этой ОС. При ошибке сборки редактор получает читаемую диагностику Rust; журналы и объём JSON ограничены.

Очистка после сборки или отмены затрагивает только подтверждённые продукты собственного worker package в default/native profile scopes. Общие зависимости и похожие пользовательские имена сохраняются. Скопированный executable живёт до последнего владельца экземпляра; Linux runnable copy остаётся на native target filesystem, даже когда исходники лежат на смонтированном Windows-диске.

Скомпилированный worker остаётся запущенным между кадрами и обменивается ограниченными JSON-lines пакетами. Это устраняет запуск нового процесса на каждом tick. Рабочее состояние хранится явно в `ctx.state` и принадлежит host; оно возвращается кандидатом вместе с командами. Host сохраняет его только после успешной проверки и применения всего пакета. При timeout, panic, неверном пакете или отклонённых командах прежнее состояние сохраняется, а worker останавливается. `static` и глобальные переменные не являются контрактом сохранения и миграции: используйте объявленное состояние. Формат, совместимость и API описаны в [custom-state.md](custom-state.md).

Текущий редакторский лимит вызова — 150 мс; API принимает явный timeout. Компиляция имеет отдельный лимит. Worker работает в корне пакета; для Team исходники Core берутся из .sdk, а game assets — из родительского пакета. SDK/lock/tools выбираются из текущей поставки; отсутствие SDK не заимствует original native workspace. Это обычный Rust с доступом к ОС, файловой системе и процессам: worker не является security sandbox. Экспортированный Player загружает заранее собранный executable и `script.json`; Rust, Cargo и SDK для такого запуска не нужны.

## Переносимое управление

ScriptContext содержит time, dt, base, objects, world_queries_available, разрешённые parameters, активные resolved properties и накапливаемые commands. В 0.4 добавлены state/state_schema, input и events. ctx.parameter/ctx.property/ctx.component_property читают настройки; global/module данные доступны через ctx.properties.global/modules. Inactive archive не передаётся. При initialized Engine policy render команды ограничены exposed ranges и ready variants, в том числе для compiled Rust. Для legacy render-only Update провайдер без чтения WorldObject может выдать контекст с objects=[] и world_queries_available=false; скрипт отличает отсутствие возможности запроса от пустого мира. Команды мира требуют соответствующей поддержки провайдера. У старого JSON-контекста без world_queries_available значение false: возможность запроса не считается заявленной.

| Мир | Рендерер |
| --- | --- |
| object(id) — чтение локального состояния. | set_render_parameter(pass, name, value) — конечный числовой scalar. |
| set_position, translate, set_transform. | enable_render_pass(pass, enabled). |
| set_color, spawn, remove. | clear_resource(name, value), copy_resource(from, to). |

Transform локален относительно parent; remove удаляет поддерево. Встроенные миры валидируют пакет целиком: ID/родителей, конечные значения, отсутствие циклов и лимиты. Ошибка не оставляет частично изменённый мир. Старый сторонний WorldProvider может поддерживать снимок сцены, но явно отказываться от редактирования.

Параметры и enabled остаются в RenderOverrides; clear/copy относятся к одному кадру. Имена ресурсов имеют вид pass_id.output_name, например geometry.color. Vulkan проверяет наличие ресурсов, совместимость формата/semantic и порядок операции относительно producer/consumer. Отключить можно только проход с допустимым совместимым bypass: например SSAO/FXAA. Проходы геометрии, смены HDR→LDR или кодирования цвета нельзя произвольно пропустить.

В Team редактируется только заранее разрешённый gameplay Update source; scalar speed и shaders принадлежат frozen Engine. Текст может быть ошибочным и сохраняться для исправления, но key set и bindings не меняются.

## Визуальные scalar-выражения

CustomProgram понимает обычную функцию без generic-параметров с именованными аргументами f64 и результатом f64; выбирает speed или единственную свободную функцию. Поддержаны последовательные let, ссылки на предыдущие bindings, конечные float-литералы f64, скобки, + - * / %, унарный минус, завершающее выражение или return expr;.

Поддержанные функции: sin, cos, tan, abs, sqrt, exp, ln, floor, ceil, round; min, max, powf, atan2; clamp. Вызовы допустимы методом или f64::function. Изменение числа/оператора и переподключение поддержанных f64-узлов меняет соответствующие диапазоны Rust. Циклы, неверный тип/порт, неизвестная типизация и использование let до определения отклоняются без изменения исходника.

Целочисленные/f32 выражения, ветвления, циклы, макросы, произвольные вызовы и влияющие на семантику attributes остаются opaque для scalar preview. Если активная функция содержит неподдержанную конструкцию, интерпретатор отказывает. При этом такой Rust может успешно компилироваться worker. syn проверяет синтаксис; общую проверку типов делает rustc.

## Визуальные команды

CommandProgram показывает известные вызовы ctx на верхнем уровне update и их параметры. Можно менять числовые литералы, строки и bool, включая отдельные значения массива позиции/цвета. Проверяются диапазоны u8/ID и конечные float; сохраняются суффиксы, комментарии и остальной Unicode-текст. Вызовы после затенения ctx рассматриваются как opaque.

Порядок команд задаёт текст Rust. Переподключение параметров команд, полноценное представление циклов/условий, функций и всех типов Rust ещё не реализованы. Они редактируются текстом и компилируются обычным образом.

## Раскладка и сохранность текста

Ручные позиции записываются в params.code_layout, а params.code_layout_keys хранит структурные ключи для сопоставления после перепарса. Редактор переносит позиции только при уникальном совпадении вида узла и его ближайших связей в старом и новом графе. Изменяемые значения литералов не входят в ключ. Неоднозначные совпадения и изменённые структуры получают стандартную позицию; это локальное сопоставление, а не постоянные AST ID. Старые code_layout без ключей читаются для сохранённых ID. Полноценная устойчивость при копировании/перемещении произвольного кода остаётся дальнейшей работой.

Исходник сохраняется даже при ошибке парсинга или компиляции. Неизвестные фрагменты не переписываются целиком; графические правки патчат поддержанные диапазоны. При синтаксической ошибке последнее корректное визуальное представление может остаться видимым, но его редактирование отключается до исправления текста.
